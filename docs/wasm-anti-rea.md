# WebAssembly（WASM）产物反 REA 选项目录（供用户选择）

> **状态**：使用指南（**非**需求基线；不修改 `SRS.md`）。
> **定位**：WASM 不是一种源语言，而是一个**编译目标**（C/C++、Rust、Go、AssemblyScript、
> Dart、Kotlin 等都能产出）。本文针对 **`.wasm` 产物本身**给出选项菜单：构建基线、IR 变换、
> 数据段处理、控制流/VM、宿主侧 native 下沉、分发完整性、运行期对抗、密钥与水印。
> 由 Agent 按 `SKILL.md` 的分阶段工作流在 **P1 方案**里呈现，**用户选定后再落地**。
> **边界**：第三方工具**不由本技能分发**；目标仍是“**抬高成本**”。

## 0. 为什么 WASM 需要单独一张菜单

| 事实 | 含义 |
| :--- | :--- |
| WASM 是**字节码**，有 type/import/function/code/data 等标准段 | 反编译/反汇编工具链成熟（`wasm2wat`、`wasm-decompile`、`wasm2c`、Ghidra 等） |
| 未 strip 时存在 **`name` 自定义段**（函数/局部变量名）与 **DWARF** | 名字与源码结构可直接读出；`-g` 产物尤其严重 |
| `sourceMappingURL`、`*.symbols`、Emscripten symbol map 是**外部线索** | 误发布等于把源码结构送出去 |
| `wasm2c` 可把模块转成 C，再进入 native 分析链 | “字节码难读”不等于安全；只是换一道工序 |
| **宿主可以读 WASM 线性内存、替换导入函数** | **WASM 不能对宿主保密**；密钥/算法放进去迟早被读 |
| AOT 缓存（wasmtime `.cwasm`、WAMR AOT、V8 优化代码）是**机器码** | 仍然可反汇编/反编译；不是“不可逆” |
| 本引擎的 IR 变换**理论上与后端无关**，可面向 `wasm32` | 但本项目**端到端只在 Linux x86_64 验证过**；wasm32 属**实验性**，须先试点 |

因此 WASM 侧的正确做法是：**先做构建基线（strip + 优化 + 不发映射）**，再把高价值核心
放到**服务端/宿主 native**；IR 变换是可选增强，但必须先做可行性验证。

> **零成本复用**：WASM 的**宿主**（Node 原生插件、Electron 原生模块、Tauri Rust 核心、
> WASI 宿主、边缘运行时）都可以回到本技能的 native 链路；把核心放到宿主 native，
> 让 WASM 只做 UI/编排，通常比在 WASM 字节码上堆混淆更划算。

## 1. 选项总览

| ID | 手段 | 攻击方要多做的 | 效果量级 | 主要代价 | 产物可移植性 | 本技能是否带工具 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **W0** | 核心逻辑放服务端/宿主 | 逆 WASM 也拿不到核心 | 最高（可做到\"无产出\"） | 需联网/宿主能力、延迟 | 不变（WASM 变薄） | 否（架构实践） |
| **W1** | 构建基线（`-O3` + strip 自定义段/DWARF + 不发映射） | 失去名字/调试信息 | 低～中（**必做**） | 排障/符号化 | 不变 | 否（wabt/Binaryen） |
| **W2** | IR 变换（本引擎 → wasm32，实验性） | 反编译/重建语义成本上升 | 中～高（未验证） | 构建链改造、性能、试点成本 | 不变（仍是 wasm） | **是**（需试点） |
| **W3** | 字符串/数据段处理（IR 加密 + 运行期解密） | 失去明文锚点 | 中 | 运行期解密开销、宿主可读内存 | 不变 | **是**（IR 侧） |
| **W4** | 控制流/VM（IR CFF/MBA/VM → wasm，实验性） | 重建控制流成本高 | 中～高（未验证） | 性能、体积、验证成本 | 不变 | **是**（需试点） |
| **W5** | 宿主侧 native 下沉（WASI host / Node addon / Electron） | 回到 native 逆向（可用本技能加固） | 高 | 逐平台产物、跨语言调试 | **部分**（宿主绑定） | **是**（加固 native 侧） |
| **W6** | 分发形态与完整性（SRI/CSP/签名/加密 at rest） | 替换/篡改模块变难 | 辅助 | 宿主/部署改造、密钥管理 | 不变 | 否 |
| **W7** | 运行期对抗（宿主校验/心跳/环境） | 动态分析变贵 | 辅助（WASM 内很弱） | 误杀、可被 patch | 不变 | 否 |
| **W8** | 密钥与信任根 + 水印 | 拿不到可用密钥；泄露可追踪 | 辅助 | 服务端/硬件依赖 | 不变 | 否 |

> **最重要的一句话**：**WASM 不能对宿主保密**。只要模块在用户可控的运行时里执行，
> 线性内存与导入函数就都在对方手里；密钥和核心算法应放服务端或宿主 native。

## 2. 选项详解

### W0 · 核心逻辑放服务端/宿主

- **原理**：授权、密钥运算、核心算法、风控放服务端 API 或宿主 native；WASM 只做 UI/编排/胶水。
- **优点**：唯一能让\"逆 WASM 也没有产出\"的路径；不受字节码可读性约束。
- **缺点**：需联网或宿主能力；有延迟与部署成本；离线纯前端场景不可用。
- **影响**：架构改造量最大；可用性/SLA 成为新的失败点；协议仍可被观察与重放。
- **获取源**：无工具，工程实践。WASM 侧可再用 W1/W6 保护加载与完整性校验。
- **适用判据**：产品本就有服务端/宿主；核心价值可服务化或 native 化。

### W1 · 构建基线（`-O3` + strip 自定义段/DWARF + 不发映射）

- **原理**：用 `-O3`/`-Oz` 优化；用 `wasm-strip` 去掉 `name`、DWARF、`sourceMappingURL`、
  producers 等自定义段；不发布 `*.symbols`、Emscripten symbol map、source map；Web 侧配 SRI。
- **效果**：函数/局部变量名与源码结构消失；反编译仍能得到语义等价的伪代码。
- **优点**：零成本、显著增加阅读成本；所有 WASM 项目的发布底线。
- **缺点**：**不是保护**——控制流、字符串、数据段仍在；`wasm2c`/`wasm-decompile` 仍可用；
  strip 后崩溃栈难以定位（需保留私有符号）。
- **影响**：CI 增加 strip/符号归档步骤；调试与线上排障要接私有符号；优化级别可能改变浮点/边界行为，需回归。
- **获取源**：wabt（`wasm-strip`、`wasm-objdump`）、Binaryen（`wasm-opt`）、各工具链的 release 选项。
- **适用判据**：**所有 WASM 产物**；先做 W1，再谈其它。

### W2 · IR 变换（本引擎 → wasm32，实验性）

- **原理**：在源侧（C/C++、Rust 的 C/FFI）用 clang `--target=wasm32` + 本引擎的 LLVM Pass，
  在生成 WASM 前施加 CFF/MBA/不透明谓词/字符串加密等变换，再由 `wasm-ld` 链接。
- **效果**：WASM 字节码层面的控制流/常量结构被改写，反编译可读性下降。
- **优点**：复用本引擎已有变换；**不需要另写 WASM 反编译器对抗**；源侧一次改造可多目标。
- **缺点**：**本项目端到端只在 Linux x86_64 验证过**，wasm32 需自行试点；WASM 后端对
  异常/尾调用/内存模型的限制可能与变换冲突；体积与性能开销需实测；调试困难。
- **影响**：构建链需改为 clang wasm32 + 插件 + wasm-ld；CI 增加 wasm 目标与回归；
  需准备“未变换”基线做功能/性能对比。
- **获取源**：clang/LLVM（`--target=wasm32`）、`wasm-ld`、本技能 `protect`（试点）。
- **适用判据**：能接受实验性、愿意先做 spike 的项目；先选 1 个小模块验证功能/性能。

### W3 · 字符串/数据段处理（IR 加密 + 运行期解密）

- **原理**：在 IR 层加密字符串常量，运行期用轻量解密写入内存；或拆分 data 段、延迟初始化。
- **效果**：`strings` 与静态检索失效；数据段不再直接暴露协议/URL/密钥派生材料。
- **优点**：与 W2 同一构建链；可按模块启用；对“随手搜字符串”效果明显。
- **缺点**：**宿主可读线性内存**，运行期解密后仍可 dump；解密例程本身是锚点；
  初始化开销与内存占用；WASM 数据段对齐/可变性需验证。
- **影响**：启动/首次调用开销；调试与内存分析变难；需回归所有字符串使用点。
- **获取源**：本技能 `string_encrypt`（IR 侧）；注意 Rust 字面量布局差异需先验证。
- **适用判据**：W2 试点通过后，作为其子项；不要单独期待“加密字符串”能挡住动态分析。

### W4 · 控制流/VM（IR CFF/MBA/VM → wasm，实验性）

- **原理**：在 IR 层做控制流平坦化、MBA、不透明谓词，或把整数叶子函数转成自定义 VM 解释。
- **效果**：控制流图与常量关系被破坏；自动反编译/模式匹配成本上升。
- **优点**：本引擎已有实现；对 wasm32 理论上后端无关；可按函数粒度。
- **缺点**：**wasm32 端到端未验证**；VM 解释器在 WASM 里运行有额外开销；体积增长；
  异常/间接调用/尾调用可能与变换冲突；仍可被动态跟踪。
- **影响**：性能/体积回归；需要 wasm 运行时（wasmtime/浏览器）功能测试；调试困难。
- **获取源**：本技能 `cff`/`mba`/`vm`（试点）；先用小模块验证。
- **适用判据**：W2 试点通过且性能可接受；只对高价值函数启用。

### W5 · 宿主侧 native 下沉（WASI host / Node addon / Electron）

- **原理**：把核心用 C/C++/Rust 实现为宿主 native 库（Node 原生插件、Electron 原生模块、
  WASI 宿主函数、Tauri Rust 核心），WASM 通过导入调用；native 侧用本技能加固。
- **效果**：核心不再在 WASM 里，回到 native 战场，可用全套手段。
- **优点**：防护强度最高；性能好（批量调用）；可复用现有 native 能力。
- **缺点**：破坏“纯 WASM 可移植”；每平台/架构各编一份；跨语言调试困难；
  浏览器环境无法使用（只能服务端/桌面/边缘宿主）。
- **影响**：构建矩阵与分发变重；需要设计导入边界与错误映射；签名/公证覆盖原生库。
- **获取源**：WASI（`https://wasi.dev/`）、Node-API、Electron native modules、Tauri；
  native 侧用本技能。
- **适用判据**：桌面/服务端/边缘场景的加密、授权、协议核心；**最推荐的换赛道方式**。

### W6 · 分发形态与完整性（SRI/CSP/签名/加密 at rest）

- **原理**：Web 侧用 Subresource Integrity + CSP 限制加载源；宿主侧校验模块哈希/签名；
  需要时对 `.wasm` 做静态加密、运行期解密后编译（密钥在宿主/服务端）。
- **效果**：替换/篡改模块、注入恶意 WASM 的门槛上升；静态抓包拿到的不是明文模块。
- **优点**：与 W1 互补；能防“CDN/缓存投毒/本地替换”这类攻击。
- **缺点**：**不防逆向**——解密后的模块仍在内存；密钥在宿主侧可被提取；
  自建加密加载器会破坏浏览器缓存/流式编译；SRI 只保护传输内容，不保护已落地文件。
- **影响**：部署/构建链增加签名与校验；密钥轮换；缓存策略调整。
- **获取源**：浏览器 SRI/CSP、WASI 运行时签名工具、自研加载器。
- **适用判据**：Web/桌面分发的完整性需求；不要把它当混淆手段。

### W7 · 运行期对抗（宿主校验/心跳/环境）

- **原理**：在**宿主**做完整性校验、环境检测、心跳与降级；WASM 内只保留最小校验钩子。
- **效果**：抬高动态调试/替换模块的成本（与 W1/W6 协同）。
- **优点**：宿主能力比 WASM 强；可与服务端联动。
- **缺点**：**WASM 内几乎没有可靠反调试**；宿主检测可被 patch；误杀（CI/无头浏览器/隐私模式）；
  对静态分析无效。
- **影响**：启动/运行开销；误杀救济；测试矩阵变大。
- **获取源**：自研（宿主哈希/环境/心跳）+ 服务端风控；商用方案需自行评估。
- **适用判据**：只作为辅助层；高价值逻辑应在 W0/W5。

### W8 · 密钥与信任根 + 水印

- **原理**：密钥放服务端/KMS/HSM 或宿主安全存储（Keychain/Keystore/DPAPI）；
  WASM 只拿短期令牌；水印用唯一常量/数据段/调用序列标记授权对象。
- **效果**：模块被逆也拿不到长期密钥；泄露可追踪。
- **优点**：让攻击产出不可直接用；水印为维权留证。
- **缺点**：**WASM 不能对宿主保密**；令牌仍可被重放；水印可被移除/伪造；
  离线纯前端场景受限。
- **影响**：密钥生命周期/轮换；服务端签发与校验；合规成本。
- **获取源**：云 KMS/HSM、平台安全存储、自研水印；商用许可证服务。
- **适用判据**：只要还发密钥到客户端/宿主，就应优先处理。

## 3. 组合阶梯（按场景推荐）

| 场景 | 建议组合 | 说明 |
| :--- | :--- | :--- |
| 所有 WASM 产物 | **W1** | strip + 优化 + 不发映射；必做 |
| 浏览器前端（无服务端核心） | **W1 + W6 + W8** | 完整性 + 短期令牌；接受\"客户端可读\" |
| 桌面/边缘（有宿主） | **W1 + W5 + W7 + W8** | 核心下沉宿主 native（本技能加固） |
| 高价值 WASM 算法 | **W1 + W2 + W3 + W4** | 先试点 wasm32；功能/性能达标再扩大 |
| 服务化产品 | **W0 + W1** | 核心上服务端；WASM 只做胶水 |

> 选择原则：**先 W1，再决定要不要碰 W2/W4**。wasm32 的 IR 变换是实验性能力，
> 没有试点数据前不要写进承诺；能放宿主 native 的，优先 W5。

## 4. 验证方法论（自证防护有效）

**攻击方视角工具**（自行获取）：

| 工具 | 许可 | 获取源 | 用途 |
| :--- | :--- | :--- | :--- |
| **wasm2wat / wasm-objdump** | Apache-2.0 | `https://github.com/WebAssembly/wabt` | 反汇编、查看段/名字/导入导出 |
| **wasm-decompile** | Apache-2.0 | wabt | 生成类 C 伪代码 |
| **wasm2c** | Apache-2.0 | wabt | 转 C 后进入 native 分析链 |
| **wasm-opt** | Apache-2.0 | `https://github.com/WebAssembly/binaryen` | 优化/对比（不是混淆器） |
| **wasm-strip** | Apache-2.0 | wabt | 去掉自定义段/DWARF（验证 W1） |
| **wasm-tools print** | Apache-2.0 | `https://github.com/bytecodealliance/wasm-tools` | 打印模块结构 |
| **Ghidra / Binary Ninja / IDA** | Apache-2.0 / 商用 | 官方 | WASM/`wasm2c` 产物反编译 |
| **strings** | binutils | 系统包 | 字符串/路径线索 |

**流程**：

1. `wasm-objdump -x` 看段与导入导出；确认 **`name`/DWARF/`sourceMappingURL` 已不存在**；
2. `wasm2wat` / `wasm-decompile` 反汇编，统计**名字可读率、控制流可读性**；
3. `strings` 统计明文比例（W3 前后对比）；
4. `wasm2c` 转 C，再用 Ghidra/IDA 分析；对比 W2/W4 前后的**重建工时**；
5. 在 wasmtime/Node/浏览器跑功能与性能基线（未变换 vs 变换）；
6. 检查分发链：SRI/CSP/签名/缓存；确认没有 `*.symbols`、source map、`-g` 产物；
7. 记录\"逆到底得到了什么\"（可用算法/密钥 = 防护不够）。

> **明确**：本技能 `verify` / `attack_sim` 面向 **LLVM 原生产物**；W2/W4 的**源侧 IR** 可用，
> 但 **wasm32 端到端未验证**；W5 的 native 部分照常使用常规链路。

## 5. 与分阶段工作流的接线（`SKILL.md`）

| 阶段 | WASM 项目怎么做 |
| :--- | :--- |
| **P0 勘察** | `anti-rea scan` 看**源语言**（C/C++/Rust 等）与构建系统；`.wasm` 是**产物**，不是源语言。画像：源语言/工具链、目标运行时（浏览器/Node/边缘/WASI）、是否可改构建（W2）、是否有宿主（W5）、是否有服务端（W0）、价值等级 |
| **P1 方案** | 从 §1 选 1–3 个组合；**W2/W4 必须标注\"实验性、需试点\"**，并给出试点模块、验收指标与回退方案，写进 `PROPOSAL.md` 交用户选择 |
| **P2 决策** | 用户可逐项取舍（如\"只做 W1\"、\"W1+W5\"、\"W1+W2 试点\"） |
| **P3 执行** | W1/W6 多为构建/分发改造；W2/W3/W4 走源侧 IR（模式 B 纪律）；改构建文件先给 diff，只加不删 |
| **P4 验证** | 按 §4 执行 WASM 侧验证；W5 的 native 部分用本技能常规链路；W2/W4 用\"未变换 vs 变换\"对照 |

## 6. 边界、许可与合规

- **不分发**：不打包、不代下载 wabt/Binaryen/wasm-tools 等，只记录获取源与用法。
- **实验性口径**：本引擎的 wasm32 支持**未做端到端验证**；不得在方案里承诺“已验证”。
- **宿主信任边界**：WASM 对宿主无秘密；不要把长期密钥、许可证私钥放进模块。
- **动态代码**：浏览器/商店对动态加载可执行代码有策略限制；加密加载器要评估合规与缓存影响。
- **不要破坏可诊断性**：保留未 strip 的私有符号/映射用于排障。
- **不改基线**：本文是\"给用户的选项\"，不是需求；需求变更走 `plan/anti-rea-project-plan.md` §10.4。
- **口径一致**：**抬高成本，不承诺不可破**。
