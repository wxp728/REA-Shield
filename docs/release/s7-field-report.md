# S7 实战补测报告：真实工程全范围构建注入 + 独立 LLM 红队（2026-10-17）

> 对应条件项：**外部第三方红队结论**（SRS NFR-02 / CQ-05）。
> 本报告为 v1.0.0 发布说明中「顺延至 S7」两项之一的补测记录；
> 另一项（NFR-02 Token 倍数 ≥ 100x）经两轮实测评估后**已废弃**，理由见 §5。

## 1. 被测对象（匿名化）

| 维度 | 描述 |
| :--- | :--- |
| 语言 | C（C99），工业级真实项目，非样例代码 |
| 平台 | Linux x86_64（RHEL 系发行版） |
| 产物形态 | **共享库 `.so`**（soname + 版本脚本导出收敛），被真实客户端程序动态加载，对运行中的数据库服务器执行真实查询 |
| 代码规模 | 8 个业务子模块 / **59 个编译单元** / 约 **10 万行 C 代码**（98.5k 行实现 + 9.4k 行头文件） |
| 业务性质 | 数据库客户端侧的加密中间层：含 SQL 语句处理器、加解密调度器、密钥/列元数据缓存、格式化器、数据取回器、硬件密码设备适配器、COPY 协议流式加密等敏感逻辑 |
| 构建系统 | 工程自身 Makefile（非工具链内置示例）；测试采用**树外构建**，目标工程源码与构建产物零改动 |

## 2. 测试方法

1. **扫描与策略**：`anti-rea scan`（子路径过滤圈定 8 个模块）→ `plan` → `buildenv --protect-all --strip`。
   识别资产 721 项（P0×517 / P1×204），保护白名单 1,221 个符号。
2. **构建注入**：同一 `clang -O2`，57 个范围内编译单元分别编译为 baseline（不挂插件）与
   protected（挂 LLVM 变换插件）两份对象，外链两个 `.so` 对照；两侧唯一差异是变换插件。
3. **功能保持验证**：两个 `.so` 分别注入真实客户端程序，对运行中的数据库服务器执行查询，
   输出逐字节一致。
4. **REA 攻击模拟**（`attack_sim --allow-llm`）：baseline / protected **各开一次全新上下文的
   独立 LLM 会话**，喂入固定中性提示 + 二进制证据（可见符号 / 字符串 / 反汇编节选，各 24k 字符封顶），
   由固定判分器对照 12 个 ground-truth 目标函数判 S1–S4。评测模型经网关调用第三方 LLM，
   与被测工程无任何关联。
5. **独立工具交叉验证**：Ghidra headless 反编译同一导出函数（baseline vs protected），
   `nm` / `strings` / `objdump` 统计符号、字符串与指令数。

## 3. 防护效果（baseline → protected）

### 静态指纹

| 项 | baseline | protected |
| :--- | ---: | ---: |
| `.symtab` 定义符号 | 2,412 | **0**（strip 生效） |
| 工程特征字符串 | 4,295 | **87**（-98%） |
| 算法关键词字符串 | 1,547 | **246**（-84%） |
| 抽样 20 个内部函数名在符号表存活 | 13 | **0** |
| 整库指令数 | 228,008 | 1,230,580（**5.4×**） |
| 动态导出符号 | 221 | 221（仅公共 API，属对外契约） |

### 关键函数指令膨胀

导出函数同名可比，最高 **13.2×**、加密编排核心函数 **11.4×**；getter 类小函数约 1.2–1.3×（保护有限）。

### 反编译可读性（Ghidra 交叉验证）

- baseline：核心批加密函数反编译输出 **778 行可读伪代码**，调度器/密钥派生等语义完整可辨；
- protected：**同一函数反编译失败**（分析器无法恢复函数体），控制流平坦化 + 不透明谓词 +
  虚拟化叠加导致静态不可读。

### 独立 LLM 红队会话

| 指标 | 结果 |
| :--- | :--- |
| 函数名恢复准确率（S2） | **0.00**（protected 会话可见符号数为 0） |
| 结构相似度 | 0.23（越低越好） |
| 功能类别判断（S1） | 0.50 —— 模型仅能从**保留的公共 API 名**与残余字符串猜测类别，未能恢复任何函数名/内部逻辑 |
| verdict | 未出现「可恢复源码级信息」的成功信号 |

## 4. 结论

1. **源码级泄漏被阻断**：命名（内部符号清零）、逻辑（Ghidra 反编译失败）、
   内容常量（特征字符串 -98%）三层均不可静态恢复。
2. **攻击成本显著抬高**：指令膨胀 5.4×（关键函数最高 13.2×）；参照此前同工程匿名盲测，
   恢复 baseline 约需半天～1 天，恢复 protected 需专家数天起步。
3. **功能零回归**：10 万行级真实工程、真实 `.so` 构建注入后行为逐字节一致。
4. **唯一残留线索是公共 API 导出名**（库的对外契约，不能也不应隐藏）；
   运行期动态调试不属静态混淆防护边界（所有混淆工具的共同边界）。
5. 定位达成：**抬高成本、而非不可破**，与 README 声明一致。

## 5. NFR-02「Token 倍数 ≥ 100x」指标：废弃

两轮真实工程实测（小型驱动程序 / 十万行级 `.so`）中该指标均恒 ≈ 1.0，评估认为
**该指标在当前判分协议下不可测、且与防护效果解耦**，理由：

1. **证据上限封顶**：喂给会话的二进制证据固定 24k 字符，两侧都被截断到同一长度，
   提示词成本天然同量级；
2. **单轮作答模式**：固定中性提示 + 一次性 JSON 回填，模型不会因为「难」而多轮消耗——
   真实 REA 是多轮交互式过程，攻击者会自行换工具、查资料、分而治之；
3. **与效果背离**：本轮 protected 侧 token 反而略低（无符号可读、输出更短），
   而实际防护效果（符号清零 / 反编译失败 / 指令 5.4×）是明确的。

**处置**：NFR-02 的 Token 倍数子项自本报告起废弃，不再作为验收门禁；
防护效果验收以「独立 LLM 会话判 S1–S4 + 静态指纹 + 独立工具（Ghidra）交叉验证」为准
（SRS 会话判定子项「上下文消耗 ≥ 90% 仍未成功即通过」保留不变）。
