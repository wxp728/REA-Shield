# Python（纯代码）反 REA 选项目录（供用户选择）

> **状态**：使用指南（**非**需求基线；不修改 `SRS.md`）。
> **定位**：本技能对**纯 Python** 不做 IR 层变换（Python 不经过 LLVM；ADR-001）；对
> **Python C 扩展**，已有能力不变（走 native 链路）。本文针对"逻辑写在 `.py` 里"的项目，
> 提供**一张选项菜单 + 每种的原理 / 优点 / 缺点 / 影响 + 获取源与用法要点**，
> 由 Agent 按 `SKILL.md` 的分阶段工作流在 **P1 方案**里呈现给用户，**用户选定后再落地**。
> **边界**：第三方工具与商用产品**不由本技能分发**；目标仍是"**抬高成本**"。

## 0. 为什么纯 Python 需要单独一张菜单

| 事实 | 含义 |
| :--- | :--- |
| 交付物通常是 `.py` 源码或 `.pyc` 字节码 | 反编译/反汇编工具链成熟（pycdc、decompyle3、pylingual 等） |
| `.pyc` 只删注释/格式，**不隐藏常量、名字、控制流** | 反编译后接近源码；`-OO` 只是去 docstring |
| 打包工具（PyInstaller / zipapp / PEX / Nuitka onefile）**都可解包** | 打包 ≠ 加密；提取后仍回到 `.pyc`/原生分析 |
| 商业壳（PyArmor 等）有公开/半公开的 unpacker | 单层壳可被针对性还原；授权与版本绑定也带来运维成本 |
| 根本约束：**CPython 必须能导入并执行字节码**（或由 C 扩展替代） | 纯 Python 的天花板很低；**真正的出口是服务端化或 native 下沉** |

因此纯 Python 侧的正确做法是：**先承认天花板，再按价值选组合**。下面 PY0–PY8 按
"攻击方要多付出什么"从高到低排列。

> **零成本复用**：Python 的 **C 扩展**（`ctypes`/`cffi`/`pybind11`/手写 C）一直属于本技能
> 的支持范围。把核心算法/授权写到 C 扩展里，比在 `.py` 里堆混淆更有效。

## 1. 选项总览

| ID | 手段 | 攻击方要多做的 | 效果量级 | 主要代价 | 产物可移植性 | 本技能是否带工具 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **PY0** | 核心逻辑上服务端 | 逆到底也只能拿到协议调用 | 最高（可做到"无产出"） | 需联网、延迟、服务端成本 | 不变（客户端变薄） | 否（架构实践） |
| **PY1** | 分发基线（不带源码、`-OO`、去调试信息） | 只能拿到 `.pyc` | 低（基线；**可反编译**） | 排障/兼容性 | 不变 | 否（标准工具） |
| **PY2** | 字节码加密/加壳（PyArmor 等） | 需 unpack/动态 dump | 中 | 商用许可、版本绑定、稳定性 | 不变 | 否（商用/自研） |
| **PY3** | 源码级字符串/控制流 | 反混淆、动态跟踪 | 低～中 | 自研 AST 工具、可读性/性能 | 不变 | 否（自研） |
| **PY4** | 编译为 C 扩展（Cython / mypyc / Nuitka） | 回到 native 分析 | 中高 | 构建链、兼容性、调试 | **部分**（逐平台 wheel） | **实验**（对生成 C） |
| **PY5** | 下沉 native（ctypes/cffi/pybind11/C 核心） | 回到 native 逆向（可用本技能加固） | 高 | 逐平台构建、跨语言调试 | **丧失**（每平台一份） | **是**（加固 native 侧） |
| **PY6** | 打包为可执行（PyInstaller / onefile / PEX） | 多一步解包 | 低 | 体积/启动、AV 误报 | 不变 | 否 |
| **PY7** | 运行期对抗（反调试/完整性） | 动态分析变贵 | 辅助 | 误杀、可被 patch | 不变 | 否 |
| **PY8** | 密钥与信任根 + 水印 | 拿不到可用密钥 | 辅助 | 服务端/硬件依赖 | 不变 | 否 |

> **最重要的一句话**：纯 Python 的静态防护**天花板很低**。如果代码必须在客户端离线运行，
> 优先考虑 **PY5（native 下沉）**；否则 **PY0（服务端）** 才是根本解。

## 2. 选项详解

### PY0 · 核心逻辑上服务端

- **原理**：授权、密钥运算、核心算法、风控放服务端 API，客户端只保留调用与展示。
- **优点**：唯一能让"逆到底也没有产出"的路径；密钥不进客户端；不受字节码可读性约束。
- **缺点**：需联网、有延迟与服务端成本；离线工具、内网隔离环境不可用。
- **影响**：架构改造量最大；可用性/SLA 成为新的失败点；协议仍可被观察与重放。
- **获取源**：无工具，工程实践。客户端可再用 PY1/PY2 保护签名校验与协议逻辑。
- **适用判据**：产品本就要联网、核心价值可服务化（SaaS、在线推理、许可证服务）。

### PY1 · 分发基线（不带源码、`-OO`、去调试信息）

- **原理**：发布物不包含 `.py`（只带 `.pyc` 或打包产物）；用 `python -OO` 去掉 docstring；
  不附带测试/调试脚本；wheel 中确认没有源码与 `.map`/调试配置。
- **效果**：攻击方拿不到原始注释与格式；**字节码仍可反编译**，名字/常量/控制流都在。
- **优点**：零成本、减小体积；所有 Python 项目的发布基线。
- **缺点**：单层基本不构成防护；不同 Python 版本的 `.pyc` 魔数不兼容；反编译工具仍可用。
- **影响**：跨版本分发需多份 `.pyc`；线上排障与 traceback 可读性下降；部分工具依赖源码。
- **工具与获取源**：CPython 自带（`compileall`、`-OO`）；打包工具见 PY6。
- **适用判据**：所有 Python 项目的第一步；**不要把它当方案**。

### PY2 · 字节码加密/加壳（PyArmor 等）

- **原理**：字节码加密 + 运行期解密/解释，或把模块放进自定义 loader；常见产品还会做
  授权绑定、过期时间、机器码。
- **效果**：静态拿到的是密文/壳；攻击方需要运行期 dump 或找 unpacker。
- **优点**：对"直接反编译"有明显阻碍；商用产品带授权/运维能力。
- **缺点**：**存在公开/半公开的 unpacker**；与 Python 版本/平台绑定；调试、打包（PyInstaller）
  与多进程/子解释器可能冲突；商用许可成本。
- **影响**：启动开销；升级 Python 需重新适配；错误栈失真；需保留"无壳"排障构建。
- **获取源**：PyArmor（`https://pyarmor.readthedocs.io/`，商用/试用）；
  自研 loader（`importlib` + 解密 + `exec`，注意安全边界）。
- **适用判据**：能接受商用许可与兼容性约束，且只把它当**一层**（配合 PY0/PY5）。

### PY3 · 源码级字符串/控制流

- **原理**：在 AST/源码层拆分或加密字符串、编码常量、改写分支（不透明谓词/平坦化）；
  可用代码生成或构建期 AST 重写。
- **效果**：`strings`/关键字检索失效；静态阅读变难。
- **优点**：无需引入运行时；可按模块/函数粒度启用。
- **缺点**：Python 的 `ast` 可被反变换；动态特性（`eval`、`getattr`、装饰器）让混淆易碎；
  对性能与可读性影响大；**没有成熟的开源 Python 控制流混淆器**。
- **影响**：构建期增加代码生成；调试困难；`inspect.getsource`、traceback、测试可能受影响。
- **获取源**：自研（`ast`/`astor`/`libcst`）；商用保护产品通常把这项与 PY2 合并。
- **适用判据**：只对少量关键常量/函数；必须完整回归。

### PY4 · 编译为 C 扩展（Cython / mypyc / Nuitka）

- **原理**：把 Python（或 `.pyx`）编译成 C，再编译为扩展模块/可执行文件；也可用 Nuitka
  直接生成 C 并调用系统编译器。
- **效果**：核心逻辑变成 native 代码，攻击方需反编译/反汇编，而不是读 `.pyc`。
- **优点**：性能通常提升；不依赖商用壳；产物是普通扩展/可执行文件。
- **缺点**：**生成代码可读性差、符号多**；Cython 只覆盖可静态类型化的子集；mypyc 要求类型注解；
  Nuitka 构建慢、产物大；调试与异常栈复杂；**本技能对"生成 C"的注入尚未验证**。
- **影响**：构建链显著变重（C 编译器、平台 wheel）；ABI/Python 版本绑定；CI 时间增加。
- **获取源**：Cython（`https://cython.org/`，Apache-2.0）、mypyc（`https://mypyc.readthedocs.io/`，
  MIT）、Nuitka（`https://nuitka.net/`，Apache-2.0）。
- **适用判据**：核心可拆成"计算密集/类型明确"的模块；**优先直接写 C 扩展（PY5）**，
  PY4 适合"已有 Python 代码、想少改"的场景。

### PY5 · 下沉 native（ctypes / cffi / pybind11 / C 核心）

- **原理**：核心用 C/C++ 实现为共享库或扩展模块，Python 只做调用；C 侧用本技能做 IR 变换。
- **效果**：核心不再以 Python 形式存在；可结合 native 全套手段。
- **优点**：防护强度最高；性能好；产物是标准 `.so`/`.pyd`。
- **缺点**：逐平台/架构各编一份；跨语言调试困难；native 崩溃会杀掉解释器；封送/异常映射成本。
- **影响**：构建矩阵与 CI 变重；wheel 需要 `manylinux`/`macosx`/Windows 多份；签名/公证覆盖。
- **获取源**：`ctypes`/`cffi`（标准库/PyPI）、pybind11（`https://pybind11.readthedocs.io/`，
  BSD-3-Clause）、CPython C API；C 侧用本技能。
- **适用判据**：加密/授权/协议/算法核心；**纯 Python 项目最推荐的换赛道方式**。

### PY6 · 打包为可执行（PyInstaller / onefile / PEX）

- **原理**：把解释器、依赖与代码打成一个可执行文件或归档。
- **效果**：分发方便；**不是保护**——PyInstaller 可被 `pyinstxtractor` 类工具解开，
  PEX/zipapp 就是 zip。
- **优点**：用户无需装 Python；部署简单。
- **缺点**：可提取、可反编译；体积大、启动慢；AV 误报；跨平台需分别构建。
- **影响**：升级/补丁需要重新打包；调试困难；与 PY2 壳可能冲突。
- **获取源**：PyInstaller（`https://pyinstaller.org/`，GPL-2.0-with-exception）、
  shiv/PEX（Apache-2.0/MIT）、Nuitka onefile。
- **适用判据**：分发便利；不纳入防护强度评估。

### PY7 · 运行期对抗（反调试 / 完整性）

- **原理**：检测 `sys.gettrace`/`pydevd`/调试器附加、校验自身文件哈希、检测注入；异常时降级。
- **效果**：抬高动态调试与自动化解包成本（与 PY2/PY5 协同）。
- **优点**：与静态手段正交；实现成本低。
- **缺点**：纯 Python 检测**很容易被 patch/绕过**；会干扰合法调试、测试与性能分析；
  对静态阅读无效。
- **影响**：误杀与支持成本；CI 需白名单；不要把检测当唯一防线。
- **获取源**：自研（`sys.gettrace`、`sys.monitoring`、哈希自校验）；商用保护产品多含此项。
- **适用判据**：只作为辅助层；高价值逻辑应已在 native 侧。

### PY8 · 密钥与信任根 + 水印

- **原理**：密钥不进客户端（服务端签发/KMS/HSM/系统钥匙串）；水印用于溯源。
- **平台能力**：`keyring`（macOS Keychain / Windows Credential Manager / Linux Secret Service）、
  服务端 KMS/HSM。
- **优点**：代码被读也拿不到可用密钥；水印为维权留证。
- **缺点**：需服务端/硬件；离线场景受限；纯 Python 客户端没有可信执行环境。
- **影响**：密钥生命周期与轮换；合规成本。
- **获取源**：`keyring`（MIT）、云 KMS/HSM、商用许可证服务。
- **适用判据**：只要还发密钥到客户端，就应优先处理。

## 3. 组合阶梯（按场景推荐）

| 场景 | 建议组合 | 说明 |
| :--- | :--- | :--- |
| 内部脚本 / 低价值 | **PY1** | 基线：不带源码、`-OO` |
| 商用离线工具 | **PY1 + PY2 + PY7** | 壳 + 检测；接受商用许可与兼容性成本 |
| 高价值离线产品 | **PY5 + PY7 + PY8** | 核心下沉 native；密钥不落客户端 |
| 已有 Python 代码、想少改 | **PY4 + PY5** | 热模块编译/下沉，其余保持 Python |
| SaaS / 在线服务 | **PY0 + PY1** | 核心上服务端；客户端只做基线 |

> 选择原则：**纯 Python 不要追求"不可读"**。要么把核心放到服务端（PY0），
> 要么放到 native（PY5）；其余手段都是辅助。

## 4. 验证方法论（自证防护有效）

**攻击方视角工具**（自行获取）：

| 工具 | 许可 | 获取源 | 用途 |
| :--- | :--- | :--- | :--- |
| **pycdc / pycdas** | GPL-3.0 | `https://github.com/zrax/pycdc` | 新版 `.pyc` 反编译/反汇编 |
| **decompyle3 / uncompyle6** | GPL-3.0 | `https://github.com/rocky/python-decompyle3` | 旧版字节码反编译（版本受限） |
| **pylingual** | 在线服务 | `https://pylingual.io/` | 新版字节码反编译（上传前评估合规） |
| **pyinstxtractor-ng** | MIT | `https://github.com/pyinstxtractor/pyinstxtractor-ng` | 解开 PyInstaller 产物 |
| **pyarmor 解包工具** | 见仓库 | 公开仓库/研究工具 | 检验 PY2 的实际强度（自行评估许可） |
| **strings / nm / objdump** | binutils | 系统包 | 原生扩展/打包产物静态线索 |

**流程**：

1. 取产物：`.pyc` / wheel / PyInstaller 目录 / 扩展 `.so`；
2. 能拿到 `.pyc` 就反编译（pycdc / decompyle3 / pylingual），统计**可读率**；
3. PY2：尝试公开 unpacker + 动态 dump，记录所需工时；
4. PY4/PY5：改用 native 方法论（`strings`/`nm`/`objdump` + 本技能 `verify`/`attack_sim`）；
5. 记录"逆到底得到了什么"（可用算法/密钥 = 防护不够）。

> **明确**：本技能 `verify` / `attack_sim` 面向 **LLVM 原生产物**，**不适用于 `.py`/`.pyc`**。
> 纯 Python 侧按本节方法论执行；PY4/PY5 的 native 部分照常使用本技能链路。

## 5. 与分阶段工作流的接线（`SKILL.md`）

| 阶段 | Python 项目怎么做 |
| :--- | :--- |
| **P0 勘察** | `anti-rea scan` 可识别 `python` 语言与 `pyproject.toml`/`setup.py`（pip）；**函数级资产面向 C 系**，Python 的敏感模块需人工补充。画像：是否联网（PY0）、是否可改构建（PY5）、是否允许商用壳（PY2）、目标平台/wheel 矩阵 |
| **P1 方案** | 从 §1 选 1–3 个组合，把原理/优缺点/影响 + §3 场景匹配 + 获取方式写进 `PROPOSAL.md`，**交用户选择** |
| **P2 决策** | 用户可逐项取舍（如"只做 PY1"、"PY1+PY5"），也可先试点 |
| **P3 执行** | 多为打包/构建改造（wheel 内容、C 扩展、壳、签名）；改构建文件先给 diff，只加不删 |
| **P4 验证** | 按 §4 执行 Python 侧验证；PY4/PY5 的 native 部分用本技能常规链路 |

## 6. 边界、许可与合规

- **不分发**：不打包、不代下载 PyArmor/Cython/Nuitka/PyInstaller 等，只记录获取源与用法。
- **许可**：PyInstaller 是 GPL-2.0-with-exception，**打包闭源程序前确认例外条款**；
  Cython/Nuitka/mypyc/pybind11 的许可相对宽松，但仍需逐项核对。
- **合规**：PyArmor 等产品的加密/绑定不得用于规避用户合法调试或违反第三方许可；
  上传代码到在线反编译服务前评估数据合规。
- **不要破坏可诊断性**：保留无壳构建与私有符号/源码映射用于排障。
- **不改基线**：本文是"给用户的选项"，不是需求；需求变更走 `plan/anti-rea-project-plan.md` §10.4。
- **口径一致**：**抬高成本，不承诺不可破**。
