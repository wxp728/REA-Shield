# Go 反 REA 选项目录（供用户选择）

> **状态**：使用指南（**非**需求基线；不修改 `SRS.md`）。
> **定位**：本技能对 Go **不做 IR 层变换**（Go 编译器不走 LLVM；ADR-001）。对 Go 服务、CLI、
> 桌面工具，本技能提供的是**一张选项菜单 + 每种的原理 / 优点 / 缺点 / 影响 + 获取源与用法要点**，
> 由 Agent 按 `SKILL.md` 的分阶段工作流在 **P1 方案**里呈现给用户，**用户选定后再落地**。
> **边界**：第三方工具**不由本技能分发**，只记录获取途径与使用要点；目标仍是"**抬高成本**"。

## 0. 为什么 Go 需要单独一张菜单

| 事实 | 含义 |
| :--- | :--- |
| Go 二进制自带 **`pclntab`**（函数名、文件路径、行号映射）、类型元数据、`go.buildinfo`（模块与依赖版本） | 即使 `-s -w` 去掉 `.symtab`/DWARF，**函数名仍可恢复**（GoReSym 等工具） |
| REA 的 provider 清单包含 **Go/Rust 元数据** | Go 目标**在其射程内**（见 [`analysis/rea-threat-analysis.md`](analysis/rea-threat-analysis.md) §2） |
| 攻击链：`strings` → `go version -m` → GoReSym 恢复符号 → 反编译/反汇编 | 未加固的 Go 二进制**接近带函数名的 native 程序** |
| 根本约束：**Go 运行时必须在二进制里**（GC、调度、反射、类型信息） | 所有手段都只能抬高成本；不能像 C 那样"删到最小" |
| cgo / `-buildmode=c-shared` 提供 **C ABI 边界** | 最值钱的核心可以下沉到 C/C++，回到本技能主战场 |

因此 Go 侧的正确做法是**按价值分层选组合**：下面 G0–G8 按"攻击方要多付出什么"从高到低排列。

> **零成本复用**：Go 通过 **cgo** 调用的 C/C++ 核心、`-buildmode=c-shared` 产出的原生库，
> 都可以直接走 [`build-injection.md`](build-injection.md) 的模式 B。**把核心算法/授权放 C 侧**
> 往往比在 Go 层做混淆更划算。

## 1. 选项总览

| ID | 手段 | 攻击方要多做的 | 效果量级 | 主要代价 | 产物可移植性 | 本技能是否带工具 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **G0** | 核心逻辑上服务端 | 逆到底也只能拿到协议调用 | 最高（可做到"无产出"） | 需联网、延迟、服务端成本 | 不变（客户端变薄） | 否（架构实践） |
| **G1** | 构建基线（`-trimpath -s -w`、去 buildinfo） | 失去路径/符号表/DWARF | 低（基线；**pclntab 仍在**） | 排障能力下降 | 不变 | 否（Go 工具链） |
| **G2** | 符号/包名/路径混淆（garble） | 用 GoReSym 也只能拿到不透明名 | 中 | 构建链替换、反射/插件兼容性 | 不变 | 否（开源工具） |
| **G3** | 字符串/常量 + 控制流 | 动态跟踪、重建语义 | 中 | 自研/工具链适配、性能 | 不变 | 否（开源/自研） |
| **G4** | 下沉 native（cgo / C 核心 / `c-shared`） | 回到 native 逆向（可用本技能加固） | 高 | cgo 开销、逐平台产物、跨语言调试 | **丧失**（每平台一份） | **是**（加固 native 侧） |
| **G5** | 换运行时/目标（TinyGo / WASM） | 换一套逆向工具链 | 中高（实验性） | 生态/兼容性受限；未验证 | 部分 | 仅 WASM 源侧（实验） |
| **G6** | 分发形态（UPX / 容器 / 自解压） | 多一步解包 | 低 | 杀软误报、启动开销 | 不变 | 否 |
| **G7** | 运行期对抗（反调试/完整性/环境） | 动态分析变贵 | 辅助 | 误杀、平台适配 | 不变 | 否 |
| **G8** | 密钥与信任根 + 水印 | 拿不到可用密钥 | 辅助 | 服务端/硬件依赖 | 不变 | 否 |

> **`-s -w` 不是保护**：它只去掉符号表与 DWARF；`pclntab` 里的函数名、文件路径、行号仍在，
> GoReSym 一类工具可以恢复。把它当"基线"，不要当"方案"。

## 2. 选项详解

### G0 · 核心逻辑上服务端

- **原理**：授权、密钥运算、核心算法、风控放服务端 API，客户端只保留调用与展示。
- **优点**：唯一能让"逆到底也没有产出"的路径；密钥不进客户端；不受 Go 元数据约束。
- **缺点**：需联网、有延迟与服务端成本；离线 CLI/内网隔离环境不可用。
- **影响**：架构改造量最大；可用性/SLA 成为新的失败点；协议仍可被观察与重放。
- **获取源**：无工具，工程实践。客户端可再用 G1/G2 保护签名校验与协议逻辑。
- **适用判据**：产品本就要联网、核心价值可服务化。

### G1 · 构建基线（`-trimpath` + `-s -w` + 去 buildinfo）

- **原理**：`go build -trimpath` 去掉本机路径；`-ldflags "-s -w"` 去掉符号表与 DWARF；
  必要时 `-buildid=`；发布物不带 `.debug`/pprof。
- **效果**：攻击方失去路径、变量级调试信息与一部分元数据；**函数名仍可从 `pclntab` 恢复**。
- **优点**：零成本、顺带减小体积；所有 Go 项目的发布基线。
- **缺点**：单层对 REA 基本无效（GoReSym 分钟级恢复符号）；排障变难。
- **影响**：线上崩溃栈需要保留私有符号化产物；pprof/追踪能力下降。
- **工具与获取源**：Go 工具链自带（`go build` / `go tool nm` / `go version -m`）。
- **适用判据**：所有 Go 项目的第一步；与 G2 搭配才有意义。

### G2 · 符号/包名/路径混淆（garble）

- **原理**：在编译前重写包/函数/类型名，去掉文件路径，破坏 `pclntab` 的语义可读性；
  `-literals` 进一步把字符串字面量拆成运行期拼接。
- **效果**：GoReSym 仍能恢复**结构**，但名字变成无意义符号；攻击方需要靠调用图/数据流重建语义。
- **优点**：开源、与 Go 构建链集成；是目前 Go 侧**性价比最高**的静态防护。
- **缺点**：反射（`reflect.Type.Name`）、`//go:linkname`、`plugin`、cgo 边界、序列化/模板按名查找
  可能被破坏；`garble` 必须与 Go 版本匹配；崩溃栈失真。
- **影响**：CI 需要替换 `go build`；测试/发布流程要回归；保留未混淆构建用于排障。
- **获取源**：`garble`（`https://github.com/burrowers/garble`，BSD-3-Clause）——
  `garble -literals -tiny build ./...`；先在小范围跑通反射/序列化回归。
- **适用判据**：所有可接受构建改造的 Go 项目；**先 G1，再 G2**。

### G3 · 字符串/常量 + 控制流

- **原理**：在 Go AST/SSA 层做字符串拆分/加密、常量编码、分支改写（不透明谓词/平坦化）；
  也可对关键函数手写等价但结构复杂的实现。
- **效果**：`strings`/关键字检索失效；调用图与常量锚点被破坏。
- **优点**：无需引入运行时；可按包/函数粒度启用。
- **缺点**：Go 生态缺少成熟的开源控制流混淆器；自研需要维护 AST/SSA 工具链
  （`golang.org/x/tools/go/ast`、`go/ssa`）；对性能与可读性影响大；易被专门工具还原。
- **影响**：构建期增加代码生成步骤；调试/panic 栈可读性下降；泛型/内联可能干扰变换。
- **获取源**：`garble -literals`（字符串）；自研 AST/SSA 重写；商用 Go 保护产品较少，需自行评估。
- **适用判据**：只对 P0/P1 资产启用；必须做完整回归与性能 A/B。

### G4 · 下沉 native（cgo / C 核心 / `-buildmode=c-shared`）

- **原理**：把敏感核心用 C/C++ 实现为静态库/共享库，Go 通过 cgo 调用；或把 Go 编译为
  `c-shared`/`c-archive` 供其它原生程序调用（后者不改变"Go 代码仍在"的事实）。
- **效果**：核心逻辑不再以 Go 形式存在，回到 native 战场，可用本技能做 IR 变换。
- **优点**：防护强度最高；C 侧可用 CFF/MBA/字符串加密/虚拟化；性能可控（批量化后）。
- **缺点**：cgo 调用有固定开销（热循环内逐次调用会显著变慢）；每平台/架构各编一份；
  跨语言调试困难；C 侧崩溃会杀掉 Go 进程；`CGO_ENABLED=0` 的静态构建不再适用。
- **影响**：构建矩阵（linux/darwin/windows × amd64/arm64）与 CI 变重；需要设计**批量化边界**；
  发布物包含原生库，签名/公证要覆盖。
- **获取源**：Go cgo（`https://pkg.go.dev/cmd/cgo`）、`-buildmode=c-shared`；C 侧用本技能。
- **适用判据**：加密/授权/协议等核心热路径；**Go 项目最推荐的"换赛道"方式**。

### G5 · 换运行时/目标（TinyGo / WASM，实验性）

- **原理**：用 TinyGo（基于 LLVM）或 `GOOS=js/wasip1 GOARCH=wasm` 改变产物形态，
  使 Go 元数据/工具链不再直接适用。
- **效果**：攻击方需要换一套分析工具（WASM 反编译/TinyGo 运行时）。
- **优点**：可能顺带减小体积（TinyGo）；WASM 可在浏览器/边缘运行。
- **缺点**：**生态受限**（TinyGo 不支持全部标准库/反射/cgo；Go WASM 体积大、性能受限）；
  本技能**未验证** TinyGo 的 IR 注入路径，不能承诺；WASM 仍可 `wasm2wat`/反编译。
- **影响**：需要重写/裁剪代码；CI 与目标平台验证成本高；不要作为唯一防线。
- **获取源**：TinyGo（`https://tinygo.org/`）、Go WASM（`https://go.dev/wiki/WebAssembly`）。
- **适用判据**：边缘/嵌入式/Web 场景的试点；先做小范围可行性验证。

### G6 · 分发形态（UPX / 容器 / 自解压）

- **原理**：对二进制做压缩壳（UPX）、放进容器/AppImage、或自解压包装。
- **效果**：多一步解包；对"随手改字符串/打补丁"有轻微阻碍。
- **优点**：便宜、成熟。
- **缺点**：**不是保护**（`upx -d` 即可还原）；UPX 常触发杀软误报；容器不隐藏代码。
- **影响**：启动开销、AV 兼容性、发布流程。
- **获取源**：UPX（`https://upx.github.io/`）、容器/打包工具。
- **适用判据**：只作为分发便利，不纳入防护强度评估。

### G7 · 运行期对抗（反调试 / 完整性 / 环境）

- **原理**：检测 `ptrace`/调试器、校验自身哈希、检测注入/篡改/虚拟化环境；异常时降级或退出。
- **效果**：抬高动态调试与自动化解包的成本（与 G2/G4 协同）。
- **优点**：与静态混淆正交、可叠加。
- **缺点**：不阻止静态分析；误报伤合法用户/CI；检测逻辑可被 patch；平台差异大。
- **影响**：启动/运行开销；需要误杀救济通道；容器/CI 环境要加白名单。
- **获取源**：自研（`ptrace(PTRACE_TRACEME)`、`/proc/self/status`、哈希自校验）；商用保护产品较少。
- **适用判据**：与 G2/G4 叠加；不单独使用。

### G8 · 密钥与信任根 + 水印

- **原理**：密钥不进客户端（服务端签发/KMS/HSM/平台安全存储）；水印用于溯源。
- **平台能力**：Linux Secret Service、macOS Keychain、Windows DPAPI、移动端 Keystore/Keychain。
- **优点**：代码被逆也拿不到可用密钥；水印为维权留证。
- **缺点**：需服务端/硬件；离线场景受限；Go 侧没有天然的"可信存储"。
- **影响**：密钥生命周期与轮换；合规成本。
- **获取源**：平台 API、云 KMS/HSM；商用保护产品多自带水印。
- **适用判据**：只要还发密钥到客户端，就应优先处理。

## 3. 组合阶梯（按场景推荐）

| 场景 | 建议组合 | 说明 |
| :--- | :--- | :--- |
| 内部 CLI / 低价值 | **G1** | 基线；顺带减小体积 |
| 商用离线 CLI | **G1 + G2** | 构建基线 + garble；先跑通反射/序列化回归 |
| 高价值离线工具 | **G1 + G2 + G4 + G7 + G8** | 核心下沉 C + 运行期对抗 + 密钥不落客户端 |
| 服务化产品 | **G0 + G1** | 核心上服务端；客户端只做基线 |
| 边缘/Web 试点 | **G1 + G5（+G4）** | 先验证 TinyGo/WASM 可行性，再决定 |

> 选择原则：**先明确"逆到底会得到什么"**。Go 的符号恢复很便宜，单靠 G1 没有意义；
> 至少 **G1 + G2**，高价值再加 G4。

## 4. 验证方法论（自证防护有效）

**攻击方视角工具**（自行获取）：

| 工具 | 许可 | 获取源 | 用途 |
| :--- | :--- | :--- | :--- |
| **go tool nm / go tool objdump** | 随 Go | Go 工具链 | 符号/反汇编（未 strip 时） |
| **go version -m** | 随 Go | Go 工具链 | 读取 buildinfo（模块/依赖/版本） |
| **GoReSym** | Apache-2.0 | `https://github.com/mandiant/GoReSym` | **从 stripped 二进制恢复函数名/行号** |
| **redress** | 见仓库 | `https://github.com/goretk/redress` | Go 二进制元数据/类型/依赖分析 |
| **Ghidra** | Apache-2.0 | `https://ghidra-sre.org/` | 反编译（配合 Go 脚本） |
| **strings / objdump** | binutils | 系统包 | 静态线索 |

**流程**：

1. 对产物跑 `go version -m`、`go tool nm`、`strings`；
2. 跑 **GoReSym**（这是判断 G1/G2 是否有效的关键），统计**符号恢复率**；
3. 用 `redress`/Ghidra 检查类型信息、依赖版本、路径泄漏；
4. 统计：函数名可读率、文件路径命中数、字符串明文比例、重建语义所需工时；
5. G4 的 native 部分改用 native 方法论：`strings`/`nm`/`objdump` + 本技能 `verify` / `attack_sim`。

> **明确**：本技能 `verify` / `attack_sim` 面向 **LLVM 原生产物**，**不适用于 Go 二进制本身**。
> Go 侧按本节方法论执行；G4 产出的原生部分照常使用本技能链路。

## 5. 与分阶段工作流的接线（`SKILL.md`）

| 阶段 | Go 项目怎么做 |
| :--- | :--- |
| **P0 勘察** | `anti-rea scan` 可识别 `go` 语言与 `go.mod` 构建标记；但**函数级资产提取面向 C 系**，Go 的敏感函数/包需在 P1 人工补充。构建画像补充：Go 版本、是否 cgo、构建矩阵、是否联网（G0）、是否可改构建（G2）、价值等级 |
| **P1 方案** | 从 §1 选 1–3 个组合，把原理/优缺点/影响 + §3 场景匹配 + 获取方式写进 `PROPOSAL.md`，**交用户选择**；G4 与 native 侧一并给预算 |
| **P2 决策** | 用户可逐项取舍（如"只做 G1+G2"、"G1+G2+G4"），也可先试点 |
| **P3 执行** | 多为构建链改造（`-trimpath`/`-ldflags`、garble、cgo、C 库）；改构建文件先给 diff，只加不删 |
| **P4 验证** | 按 §4 执行 Go 侧验证；G4 的 native 部分用本技能常规链路 |

## 6. 边界、许可与合规

- **不分发**：本技能不打包、不代下载 garble/GoReSym/UPX 等第三方工具，只记录获取源与用法。
- **反射与序列化**：garble 会改名，`encoding/json`、模板、ORM、RPC 按名查找需保留规则并回归。
- **cgo 约束**：G4 会失去 `CGO_ENABLED=0` 的纯静态构建；交叉编译需要对应 C 工具链。
- **UPX 误报**：G6 可能触发杀软；企业分发前先评估。
- **不改基线**：本文是"给用户的选项"，不是需求；涉及需求变更走 `plan/anti-rea-project-plan.md` §10.4。
- **口径一致**：**抬高成本，不承诺不可破**；不针对 REA 工具本身做任何攻击。
