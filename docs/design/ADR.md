### ADR-001 IR 变换采用 LLVM 18+ Pass 插件，并锁定版本

- **状态**：已接受
- **背景**：需要在编译级实施 CFF / MBA / 不透明谓词等变换（FR-C1…C5），且要求语义等价、可复现。
- **决策**：以 LLVM Pass 插件形式实现，版本锁定为 LLVM 18+；升级走独立适配分支。
- **备选**：MLIR（生态不如 LLVM 成熟）；源码级文本变换（语义不可控）。
- **后果**：获得强 IR 分析与改写能力；代价是绑定 LLVM 版本，需维护升级适配（风险登记册已登记）。
- **验证**：PoC-1 ✅ **通过**（2026-10-15）。LLVM 18.1.8 + New PM 插件对样例函数完成 CFF；**关键结论**：需先 `reg2mem` 消除跨块 SSA 依赖，且变换须在优化流水线末端执行（否则被 SimplifyCFG 还原）。证据见 `poc/poc1-llvm-pass/`、`poc-plan.md §6`。

### ADR-002 虚拟化引擎自研（自定义 ISA + VM）

- **状态**：已接受（待 PoC 验证核心可行性）
- **背景**：代码虚拟化是 P0 资产的核心防护（FR-C7），且需逐实例随机化 ISA 以获得差异化能力。
- **决策**：自研虚拟化引擎（自定义 ISA、字节码编译、解释器嵌入），参考 ASGARD-5877 的多架构设计；不封装 Tigress。
- **备选**：Tigress（成熟但同质化、难差异化）；开源 VMP（能力与可维护性受限）。
- **后果**：获得差异化能力与可控的 ISA 随机化；代价是研发成本高、需自行保证语义等价。
- **验证**：PoC 由 R2 迭代承担；本阶段先冻结接口与 ISA 规范骨架。

### ADR-003 白盒密码 v1.0 走自研查找表编码

- **状态**：已接受（PoC-4 ✅ 通过，2026-10-15）
- **背景**：需保护客户端 AES / SM4 密钥（FR-C10）。威胁模型定位为「提高提取成本」，而非抵抗专业 DCA / 侧信道。
- **决策**：v1.0 实现**自研查找表编码**（轻量：S-box 查表 + 编码变换隐藏规律 + 运行时密钥重构与销毁）；Chow 白盒作为后续增强。
- **备选**：标准 Chow 白盒 AES（体系完整但实现复杂，且已知可被 DCA 攻击）。
- **后果**：落地快、成本可控；防护强度有限，须在威胁模型声明中如实标注。
- **验证**：PoC-4 ✅ **通过**（2026-10-15）：编码查找表 AES 通过 FIPS-197 向量、加解密往返与 1000 次随机一致性；二进制无明文密钥常量；整块加密开销 1.05×。证据见 `poc/poc4-wbc/`、`poc-plan.md §6`。

### ADR-004 评估 LLM 不绑定供应商，采用独立会话 + 上下文消耗判定

- **状态**：已接受
- **背景**：量化防护效果需要 LLM 做 REA（FR-E3），但固定供应商会带来成本、可用性与数据外发问题。
- **决策**：评估使用 **Agent 运行环境所提供的 LLM**（含本会话模型），不绑定固定供应商；判定口径为「给 LLM 一个**独立会话**执行 REA，**上下文消耗 ≥ 90% 仍未成功**即判通过」；同时保留 Token 消耗倍数等量化指标。
- **备选**：固定商业 API（成本 / 配额 / 数据外发）；纯本地模型（效果弱、需硬件）。
- **后果**：无需单独 API 预算、与模型无关；代价是判定具相对性（依模型强弱而变），故量化指标并行保留；「REA 成功」定义待 OI-07 在 S2 细化。

### ADR-005 变换插件采用进程内 SPI + 能力声明

- **状态**：已接受
- **背景**：需要新变换可插拔而不改核心引擎（FR-C11），并支持预算预测。
- **决策**：进程内插件 SPI，导出 `register_plugin()`；插件声明 `capabilities()`（名称、适用类型、参数 Schema、开销估计、覆盖率支持）；宿主做版本与参数校验。
- **备选**：子进程 / 沙箱隔离（更强隔离，但复杂、性能差）。
- **后果**：简单高效；不可信插件沙箱列为后续增强（当前仅加载可信插件）。
- **验证**：PoC-3 ✅ **通过**（2026-10-15）：以「策略基因（策略开关 + 参数）」形式表达策略组合并跑通一轮进化循环，最优个体可导出并通过 `protection_policy` schema 校验，佐证「策略即数据 + 插件能力声明」的可插拔设计。证据见 `poc/poc3-deap/`、`poc-plan.md §6`。

### ADR-006 外部工具经适配层隔离，锁定版本

- **状态**：已接受
- **背景**：Ghidra Headless 与 LLVM 的 API / CLI 可能随版本变化，威胁评估链路的稳定性。
- **决策**：对 Ghidra、LLVM 的调用统一经适配层封装，锁定版本；变更集中在该层处理。
- **备选**：直接依赖上游 API（耦合高、易断）。
- **后果**：隔离外部变化；代价是多一层间接。
- **验证**：PoC-2 ✅ **通过**（2026-10-15）：PyGhidra 批量反编译 3 个样例二进制成功率 100%（57/57）。**关键结论**：Ghidra 12 已移除内置 Jython，适配层须以 **PyGhidra（CPython）** 或 Java 为基座，并将 Ghidra 版本与 `pyghidra` 一并锁定。证据见 `poc/poc2-ghidra-headless/`、`poc-plan.md §6`。

### ADR-007 平台支持顺序：Linux 优先，产物含 Windows 为 Must

- **状态**：已接受（对应 SRS OI-01）
- **背景**：LLVM 工具链在 Linux 上更成熟；用户需要保护的目标程序可能运行在 Windows。
- **决策**：**产物目标平台** Linux x86_64 / arm64、Windows x64 均为 Must；**工具自身运行平台** Linux / WSL2 为 Must、原生 Windows 为 Should。
- **备选**：工具原生 Windows 也设为 Must（工作量与风险显著上升）。
- **后果**：v1.0 必须交付 Windows 目标产物支持；工具原生 Windows 可延后。
