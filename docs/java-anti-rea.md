# Java / Android 反 REA 选项目录（供用户选择）

> **状态**：使用指南（**非**需求基线；不修改 `SRS.md`）。
> **定位**：本技能对 Java **不做 IR 层变换**（ADR-006）。对 Java / Android 项目，本技能提供的是
> **一张选项菜单 + 每种的原理 / 优点 / 缺点 / 影响 + 获取源与用法要点**，由 Agent 按
> `SKILL.md` 的分阶段工作流在 **P1 方案**里呈现给用户，**用户选定后再落地**。
> **边界**：第三方工具与商用加固产品**不由本技能分发**——这里只记录获取途径与使用要点；
> 许可、试用与合规由用户自行确认。目标仍是"**抬高成本**"，不追求"不可破"。

## 0. 为什么 Java 需要单独一张菜单

| 事实 | 含义 |
| :--- | :--- |
| REA（6.5.0）的 provider 含 **JEB**、**apktool（APK）**、浏览器（Playwright/CDP）、ASAR/JS 树 | Java / Android 目标**在其射程内**（见 [`analysis/rea-threat-analysis.md`](analysis/rea-threat-analysis.md) §2） |
| 字节码保留常量池：类/方法/字段名、字符串、类型、行号 | 反编译器（jadx / CFR / Vineflower / Procyon / JEB）能**近乎还原源码** |
| 攻击链极短：`unzip → 反编译 → 读源码`；LLM 对 Java 的熟悉度最高 | **未加固的 jar 基本等同交付源码**——用 C/C++ 的成本直觉会严重低估风险 |
| 根本约束：**JVM 必须执行完整字节码** | 所有手段都只是抬高还原成本；Java 侧天花板低于 native |

因此 Java 侧的正确做法不是"找一种工具"，而是**按价值分层选组合**：下面 J0–J8 按"攻击方要多付出什么"从高到低排列。

## 1. 选项总览

| ID | 手段 | 攻击方要多做的 | 效果量级 | 主要代价 | 产物可移植性 | 本技能是否带工具 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **J0** | 核心逻辑上服务端 | 逆到底也只能拿到协议调用 | 最高（可做到"无产出"） | 需联网、延迟、服务端成本 | 不变（客户端变薄） | 否（架构实践） |
| **J1** | 精简 + 名称混淆 | 重建符号语义，靠数据流猜名字 | 低（基线，小时级） | keep 规则维护、mapping 管理 | 不变 | 否（开源工具，见 §2） |
| **J2** | 字符串/常数加密 + 控制流混淆 | 换反编译器、跑动态跟踪、手工还原 CFG | 中（小时～天级） | 商用许可、启动/调试体验下降 | 不变 | 否（商用/自研） |
| **J3** | 类加密 + 自定义 ClassLoader（加壳） | 必须**运行期 dump** 才能继续 | 中高 | 启动开销、类加载兼容性 | 不变 | 否（商用/自研壳） |
| **J4** | 字节码虚拟化（VMP 类） | 逆解释器、重建自定义 ISA | **Java 层单点最高** | 工具稀缺、性能降几十倍 | 不变 | 否（商用/自研） |
| **J5** | 下沉 native（JNI / JNA / Panama FFM） | 回到 native 逆向（可用本技能加固） | 高 | 逐平台产物、跨语言调试 | **丧失**（每平台一份） | **是**（本技能加固 native 侧） |
| **J6** | GraalVM native-image（整体 AOT） | 逆原生二进制，且失去 Java 符号锚点 | 高（一次到位） | 闭世界配置、构建慢、逐平台 | **丧失** | **是**（对本技能能力面友好） |
| **J7** | 运行期对抗（反调试/完整性/环境） | 动态 dump 与自动化批量攻击变贵 | 辅助（与 J3/J4 协同） | 误杀风险、平台适配 | 不变 | 否（商用 RASP/自研） |
| **J8** | 密钥与信任根 + 水印 | 拿不到可用密钥；泄露可溯源 | 辅助 | 服务端/硬件依赖 | 不变 | 否 |

## 2. 选项详解

### J0 · 核心逻辑上服务端

- **原理**：把授权、密钥运算、核心算法放到服务端 API，客户端只保留调用与展示。
- **优点**：唯一能让"逆到底也没有产出"的路径；不受 JVM 约束；密钥不进客户端。
- **缺点**：需联网、有延迟与服务端容量成本；离线软件、嵌入式、无网环境**不可用**。
- **影响**：架构改造量最大（往往重写模块边界）；可用性/SLA 成为新的失败点；客户端协议仍可被观察。
- **获取源**：无工具，工程实践。客户端可再用 J1/J2/J5 保护签名与协议逻辑。
- **适用判据**：产品本来就要联网、核心价值可服务化。

### J1 · 精简 + 名称混淆（基线，必做）

- **原理**：删除未使用代码，把包/类/方法/字段重命名成无意义短名。
- **效果**：攻击方失去"名字即文档"的锚点（`LicenseValidator.checkActivation` 这类语义泄漏消失），必须靠数据流/调用图重建语义；**反编译本身仍然成功**。
- **优点**：开源、零许可成本；顺带减小体积、加快加载；**任何 Java 项目都该先做**。
- **缺点**：单层 J1 对 REA 通常只是"失去名字"，字符串、常量、控制流完好——有经验的攻击方**小时级**即可读通。
- **影响**：需维护 keep 规则（反射、序列化、JNI 符号、注解处理器、RMI、资源名）；栈跟踪要靠 mapping 还原；发布必须归档 mapping 以保证可复现；线上崩溃定位变难。
- **工具与获取源**：

  | 工具 | 许可 | 获取源 | 用法要点 |
  | :--- | :--- | :--- | :--- |
  | **ProGuard** | GPLv2 | `https://github.com/Guardsquare/proguard`（文档 `guardsquare.com/proguard`） | `java -jar proguard.jar @config.pro`；`-keep` 保公共 API，`-printmapping` 存映射 |
  | **R8**（含 D8） | Apache-2.0 | Android SDK build-tools；`https://r8.googlesource.com/r8` | Android：AGP 下 `minifyEnabled true` + `proguard-rules.pro`（R8 用 ProGuard 规则格式）；命令行 `java -cp r8.jar com.android.tools.r8.R8 --release --pg-conf rules.pro --lib <rt.jar> in.jar` |
  | **yGuard** | MIT | `https://github.com/yWorks/yGuard`（Maven 插件 `yWorks/yguard-maven-plugin`） | Ant/Gradle task；官方说明可处理到 Java 21 编译的 `.class`；XML 规则 + 输出 rename 日志 |

- **适用判据**：所有 Java/Android 项目的第一步；先跑通"混淆后功能回归 + mapping 落库"。

### J2 · 字符串/常数加密 + 控制流混淆

- **原理**：字面量与整数常量在运行期解密；分支/循环改写为**无源码对应结构**（不透明谓词、平坦化），部分类/方法可加密。
- **效果**：REA 赖以闭合的 `strings`/常量锚点失效；反编译产物出现非法 `goto`、缺块或直接失败——攻击方从"读源码"退化到"读字节码 + 动态观察"。
- **优点**：不动架构、可按类/方法粒度启用；对"LLM 读反编译文本"这条最省力的攻击路径打击最明显。
- **缺点**：商用许可成本；反编译失败 ≠ 不可解——攻击方可换反编译器或改用 Java Agent/Instrumentation、调试断点做动态还原。
- **影响**：解密与膨胀分支带来启动/运行开销（通常可控）；调试与栈跟踪可读性下降；反射调用需工具支持；需跟随 JDK 新版本升级工具。
- **工具与获取源**（商用，官方渠道获取/试用）：

  | 工具 | 获取源 | 关键能力 |
  | :--- | :--- | :--- |
  | **Zelix KlassMaster** | `https://www.zelix.com/klassmaster/`（文档 `.../docs/`） | 名称/流混淆、字符串与整数常数加密、方法参数混淆、引用混淆、AutoReflection、增量混淆、ZKM Script 与构建工具接口 |
  | **Allatori** | `https://www.allatori.com/` | 字符串加密、流混淆、水印、增量 |
  | **DashO**（PreEmptive） | `https://www.preemptive.com/` | 重命名、字符串加密、控制流、篡改/调试检测、水印（Java 与 Android） |

  **自研路线**：基于 ASM / ByteBuddy 做常量加密与 CFG 改写。研究原型（JBCO、SandMark 等）多已停更，仅作**技术参考**。

- **适用判据**：只对 P0/P1 资产（授权、算法、协议）启用重混淆，P2 保持轻量，避免全局开销。

### J3 · 类加密 + 自定义 ClassLoader（加壳）

- **原理**：发布物里的类文件被加密，运行期由自定义 ClassLoader 解密后 `defineClass`；静态只看到密文与解密器。
- **效果**：静态分析**没有字节码可读**，攻击方必须运行期 dump（attach agent、内存 dump、脱壳脚本）。
- **优点**：静态防护强度显著高于 J1/J2，可叠加在 J2 之上；Android 侧是成熟做法（DEX 加壳）。
- **缺点**：只抬高**静态**闭合成本——配合 J7 才真正难打；对启动耗时与类加载兼容性有要求；受限类加载、JPMS 强封装、AOT/native-image 场景难做或不可用。
- **影响**：启动开销（解密 + 校验）；可能与依赖自定义类加载/反射的框架冲突；需要保留"无壳降级"路径。
- **获取源**：商用加固套件（含 RASP 的加固产品、Android 加固厂商产品线）或自研（自定义 ClassLoader + APK 签名校验 + 多 dex）。
- **适用判据**：有明确"防静态抄源码"诉求，且产品能接受启动开销与兼容性约束。

### J4 · 字节码虚拟化（VMP 类，Java 层单点最高）

- **原理**：把敏感方法编译成**自定义指令集**（虚拟寄存器/栈 + 随机化 opcode 映射）并内嵌解释器，JVM 只执行解释器。
- **效果**：攻击方必须逆那个解释器、重建自定义 ISA 与映射，才能恢复语义——**把"读源码"变成"写反编译器"**，是对抗自动化 REA 最有效的手段。
- **优点**：单点成本抬升在 Java 层最大；与 J2/J3 叠加后形成完整纵深。
- **缺点**：实现门槛高、独立工具稀缺（多为商用加固或自研；学术原型基本停更）；与反射、异常、调试的兼容性复杂。
- **影响**：被虚拟化方法运行开销可达**几十倍至两个数量级**（解释执行）——只适合极少数热点/关键方法；体积增大；异常栈与调试信息失真。
- **获取源**：商用加固产品（含 RASP 的套件）或自研；学术参考 *SoK: Automatic Deobfuscation of Virtualization-protected Applications*（`https://dl.acm.org/doi/10.1145/3465481.3465772`）。
- **适用判据**：只挑 2–5 个最敏感方法；必须做性能 A/B，并留运行期回退开关。

### J5 · 下沉 native（JNI / JNA / Panama FFM）

- **原理**：把敏感核心用 C/C++ 实现成原生库，Java 侧只做调用；原生二进制回到 **LLVM 战场**——正是本技能的主战场（可挂 CFF/MBA/字符串加密/虚拟化/白盒密码）。

| 接口 | 机制 | 单次调用开销 | 适用 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| **JNI** | JVM 内置，`javac -h` 生成头文件 | **最低**（约 0.1–1 µs/次，绝对值低） | 热路径、性能核心 | 需手动管理引用/内存，出错可崩 JVM；每平台一份产物 |
| **JNA** | libffi 运行期动态派发 | **高**（比 JNI 慢 10–100×） | 低频调用、调系统库 | 无需编译胶水代码；**不适合热路径** |
| **Panama FFM**（`java.lang.foreign`） | JDK 官方 FFM API | 接近 JNI，明显优于 JNA | Java 22+ 新代码 | JEP 454 在 JDK 22 定稿；Arena 管理生命周期更安全；无需手写胶水 |

- **优点**：防护强度直接跳到 native 量级；计算密集段常**更快**；核心逻辑既不上服务端也不裸露在字节码里。
- **缺点**：**可移植性在"产物"层丧失**——每个平台各编一份；跨语言边界调试困难；JNI 引用/内存管理易错；native 层崩溃会直接杀掉 JVM。
- **影响**：构建矩阵增加（linux-x64 / linux-arm64 / macos / windows）；包体增大；不允许 JNI 的托管/沙箱环境不可用。
- **获取源**：JNI（JDK 内置，Oracle JNI 规范）；JNA `https://github.com/java-native-access/jna`（LGPL-2.1 / Apache-2.0 双许可）；FFM `https://openjdk.org/jeps/454`。
- **用法要点**：设计**批量化边界**（一次调用做完一段工作，绝不让热循环跨边界）；native 侧用本技能做 IR 变换 + 导出收敛，并沿用 `docs/build-injection.md` 的构建注入。

### J6 · GraalVM native-image（整体 AOT）

- **原理**：构建期把整个应用 AOT 编译为原生可执行文件，字节码与常量池不复存在。
- **效果**：REA 从"反编译 Java"退回"逆原生二进制"，同时**失去 Java 的符号/常量锚点**——成本量级上升，且可用本技能继续加固。
- **优点**：一次到位（整应用换赛道）；启动毫秒级、内存占用小（容器/Serverless 收益明显）；可做无 JVM 分发。
- **缺点**：**闭世界分析**——反射、动态代理、资源需显式配置（用 tracing agent 生成）；部分库/框架不兼容；构建时间从秒级变**分钟级**；稳态性能在未做 PGO 时可能落后 HotSpot 10–30%（PGO 后可追平甚至反超）；**逐平台产物**；JVMTI 等诊断手段受限。
- **影响**：CI 变慢；发布矩阵 ×N 平台；行为差异需完整回归测试。
- **获取源**：`https://www.graalvm.org/downloads/`。**许可**：Oracle GraalVM 25.x / 21.x 更新按 **GFTC**（生产免费使用、可再分发但不得收费），CE 为 GPLv2 + Classpath 例外；Native Image 属 Early Adopter 技术。
- **用法要点**：先用 tracing agent 采集 `reachability metadata`（`-agentlib:native-image-agent=config-output-dir=...`），全量测试通过后再上 PGO。

### J7 · 运行期对抗（反调试 / 完整性 / 环境检测）

- **原理**：检测调试器/Agent/Instrumentation、校验自身完整性（签名/哈希）、检测篡改与 ROOT/越狱；异常时降级或拒绝继续。
- **效果**：抬高"动态 dump、单步跟踪、脚本化批量攻击"的成本——**尤其与 J3/J4 配合**（它们迫使攻击方转动态）。
- **优点**：与静态混淆正交、可叠加；把便宜的分析变成要花人力的分析。
- **缺点**：不阻止静态分析；误报会伤合法用户、调试与无障碍工具；检测逻辑本身可被 patch。
- **影响**：启动/运行检测开销（通常可控）；平台适配成本；需设计**被检测后的救济通道**（合规与支持成本）。
- **获取源**：商用加固 / RASP 套件（多数带有篡改、调试、环境检测能力）；Android 侧 Root/调试检测实践成熟；亦可自研。
- **用法要点**：检测失败**降级而非崩溃**，避免误杀灾难；留取证日志；不把检测当作唯一防线。

### J8 · 密钥与信任根 + 水印

- **原理**：密钥不进客户端（服务端签发 / HSM / TEE / Keystore-StrongBox / SE）；水印用于**溯源**而非防护。
- **优点**：即使代码被逆，拿不到可用密钥 → 攻击产出不可直接用；水印为维权留证。
- **缺点**：需要服务端或硬件能力；离线场景受限；白盒密码在 Java 侧尚未成熟到可放心使用（属另一类工程）。
- **影响**：架构与运维改动；硬件依赖（TEE 可用性因设备而异）。
- **获取源**：平台能力（Android Keystore/StrongBox、Apple Secure Enclave）；服务端 HSM/KMS；商用加固多自带水印。
- **适用判据**：只要还发密钥到客户端，前面的混淆都可能是"给锁配了把公开的钥匙"。

## 3. 组合阶梯（按场景推荐）

| 场景 | 建议组合 | 说明 |
| :--- | :--- | :--- |
| 内部工具、低价值 | **J1** | 基线，顺带减小体积 |
| 商用小工具、本就要联网 | **J0 + J1** | 关键逻辑上服务端，客户端做基线混淆 |
| 商用离线桌面 / CLI | **J1 + J2 + J5** | 名字/常量/控制流 + 核心下沉 native；可评估叠加 J6 |
| 可承受架构改造的高价值离线产品 | **J6 + J5 + J7** | 整体 native 化 + 核心再用本技能加固 + 运行期对抗 |
| Android 商用 | **J1/J2（R8 或 DexGuard）+ J3/J4（加固壳）+ J5（native 核心）+ J7** | 多层纵深，业界常态 |
| 预算充足、需最强 | **J0 或 J6 + J4 + J7 + J8** | 多层叠加，且密钥不落客户端 |

> 选择原则：**先明确"逆到底会得到什么"**。如果答案是"一个 HTTP 调用"，J0 就够；如果必须离线交付完整客户端，就往 J1→J2→J5/J6→J4 逐级叠加，并始终配 J8。

## 4. 验证方法论（自证防护有效）

**攻击方视角工具**（自行获取；REA 亦使用其中的 JEB 与 apktool）：

| 工具 | 许可 | 获取源 | 用途 |
| :--- | :--- | :--- | :--- |
| **jadx** | Apache-2.0 | `https://github.com/skylot/jadx` | jar/apk → 可读源码；自带 GUI/CLI |
| **CFR** | MIT | `https://www.benf.org/other/cfr/` | 现代字节码反编译质量高 |
| **Vineflower** | Apache-2.0 | `https://github.com/Vineflower/vineflower` | Fernflower 分支，命令行批量反编译 |
| **Procyon** | Apache-2.0 | `https://github.com/mstrobel/procyon` | 备选反编译器（交叉验证） |
| **javap** | JDK 内置 | 随 JDK | `javap -p -c` 字节码级核对 |
| **apktool** | Apache-2.0 | `https://github.com/iBotPeaches/Apktool` | Android APK 反编译（对齐 REA 能力） |

**流程**：

1. 加固产物 → 跑 2–3 个反编译器（**交叉验证**，单一工具的失败不算数）；
2. 统计可量化指标：**命名可读率**、**字符串明文比例**、**反编译失败/异常率**；
3. 尝试重建可编译源码并**计时**（工时是最终成本指标）；
4. 记录"逆到底得到了什么"（能拿到可用算法/密钥 = 防护不够）。

> **明确**：本技能的 `verify` / `attack_sim` 面向 **LLVM 原生产物**，**不适用于 Java 字节码**。
> Java 侧按本节方法论执行（**本技能提供方法论与口径，不代跑**）；若核心已下沉 native（J5/J6），
> 则对 native 部分照常使用 `verify` / `attack_sim`。

## 5. 与分阶段工作流的接线（`SKILL.md`）

| 阶段 | Java 项目怎么做 |
| :--- | :--- |
| **P0 勘察** | `anti-rea scan` 可识别 `java`、`gradle`/`maven` 构建标记；构建画像补充：JDK 版本、构建工具、产物形态（jar / aar / apk / jlink / native-image）、是否 Android、是否允许联网（决定 J0 可行性） |
| **P1 方案** | 从 §1 表里选 1–3 个候选组合，把每种候选的**原理 / 优点 / 缺点 / 影响**摘要 + §3 的场景匹配 + **依赖获取方式**写进 `PROPOSAL.md`，**交用户选择**；与 native 侧（J5/J6 里的本技能部分）一并给出代价预算 |
| **P2 决策** | 用户可逐项取舍（例如"只做 J1 基线""J0+J5""J6+J7"），也可要求先做小范围试点 |
| **P3 执行** | 多为**构建/发布流程改造**（Gradle/R8 配置、插件接入、native 模块编译、native-image 配置）；按模式 B 的纪律：**改构建文件先给用户看 diff，只加不删** |

## 6. 边界、许可与合规

- **不分发**：本技能不打包、不代下载上述第三方工具与商用产品，只**记录获取源与用法**；商业许可与试用条款由用户与厂商确认。
- **许可影响**：混淆/加壳可能影响**开源许可义务**（例如 GPL 组件、Classpath 例外、再分发条款）与第三方 SDK 的条款，落地前须自查。
- **不改基线**：本文是"给用户的选项"，不是需求；涉及需求变更走 `plan/anti-rea-project-plan.md` §10.4 流程。
- **口径一致**：与 native 侧同一立场——**抬高成本，不承诺不可破**；不针对 REA 工具本身做任何攻击。
