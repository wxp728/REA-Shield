## 1. 引言

### 1.1 目的

本 SRS 将 Anti-REA Skill 的项目定位与能力方案（`anti-rea-plan.md`）规格化为可追踪、可验收的需求基线，作为后续概要设计、详细设计、编码与测试的唯一需求来源。

### 1.2 范围

Anti-REA Skill 是一个 AI Agent 可调用的代码工程**反逆向加固技能**：接收代码工程（源码或二进制），自动施加多层级防护变换，将 AI 驱动逆向工具（REA 类）的**逆向成本推高至高于逆向收益**，而非追求理论上的「不可逆向」。本 SRS 覆盖完整流水线：资产扫描 → 策略决策 → 变换执行 → 构建集成 → 评估验证 → 对抗策略引擎。

### 1.3 术语与缩略语

| 术语 | 含义 |
| :--- | :--- |
| REA | Reverse Engineer Anything，AI 驱动的逆向工具 |
| CFF | Control Flow Flattening，控制流平坦化 |
| MBA | Mixed Boolean-Arithmetic，混合布尔算术（表达式混淆） |
| VMP | 代码虚拟化（Virtual Machine Protection） |

## 2. 总体描述

### 2.1 产品愿景与设计哲学

**核心目标不是「让代码不可逆向」，而是「让逆向成本 > 逆向收益」。** 传统混淆依赖「保护时间 vs 逆向时间」的不对称，而 LLM 正在逆转该不对称；本产品的使命是重新扳回不对称，以「Token 消耗倍数」「分析时间倍数」等攻防经济学指标衡量成功。

### 2.2 产品范围与边界

**范围内（v1.0）**

- 对代码工程执行资产扫描、策略决策、变换执行、构建集成、效果评估的端到端流水线；
- 支持 LLVM 生态语言（C/C++/Rust）为主目标，Python/JS/Java 等提供扫描与轻量混淆能力；
- 提供 CLI、构建系统插件与 MCP Server 三种使用形态；
- 内置 AI 攻击模拟与量化评估，支持策略持续进化。

**范围外（v1.0 明确不做，Won't）**

| 项 | 说明 |
| :--- | :--- |
| RISC-V 虚拟化后端 | 方案提及多架构，但 v1.0 仅承诺 x86_64 / ARM64 |
| WASM / Android 平台 | 归入后续版本，NFR-05 标为扩展 |
| IDA Pro 集成 | 攻击模拟仅基于 Ghidra Headless（开源可自动化） |
| 「抗提取」白盒密码 | 威胁模型定位为「提高提取成本」，不承诺抵抗专业 DCA/侧信道 |
| 对开源组件施加变换 | 明确禁止（许可证合规，见 CQ-01） |

### 2.3 干系人（RQ-01）

| 角色 | 关注点 | 与产品的关系 |
| :--- | :--- | :--- |
| AI Agent | 可编程调用、结构化输出、可靠幂等 | 主要使用方，经 MCP / CLI 调用 |
| 安全工程师 | 策略可控、效果可量化、威胁模型清晰 | 策略定制与效果评估 |
| 构建 / 发布工程师 | CI 可嵌入、失败可控、产物可复现 | 集成到构建流水线 |
| 产品 / 交付团队 | 分发产物不被安全软件误杀、符合法规 | 消费保护产物 |
| 维护者（Anti-REA） | 策略库可演进、外部依赖可控 | 引擎与策略库进化 |
| 合规 / 法务 | 许可证、出口管制、使用边界 | 治理与审查 |
| 人工技术负责人 | 里程碑门禁审批 | 审批 M0–M8 出口 |

### 2.4 运行环境（RQ-01）

| 维度 | 说明 |
| :--- | :--- |
| 开发环境 | Linux / WSL2 为第一优先；Windows x64 作为适配目标 |
| 运行环境 | 本机 CLI、容器化、或作为 MCP Server 接入 Agent；默认离线可运行 |
| 必需依赖 | LLVM 18+、Ghidra（Headless，版本锁定）、Python 3.11+、Node 20+、DEAP、YAML / JSON Schema 校验器 |
| 可选依赖 | LLM 服务（攻击模拟与策略进化，可配置私有模型）；目标平台真机 / 模拟器（动态验证） |

### 2.5 设计约束

- **语义等价**：任何变换不得改变程序可观测行为，须经差分测试 / SMT 验证。
- **许可证**：不得对开源组件施加变换，须保留许可证声明。
- **预算**：变换强度受性能预算约束（见 NFR-01）。
- **可复现**：随机性必须由种子控制（见 NFR-04 / NFR-08）。
- **本土化 ISA**：虚拟化引擎的自定义 ISA 须逐实例随机化，防止一次分析通吃。
- **审计**：拒绝执行、加密强度、LLM 出站等行为须留痕（见 CQ-02 / CQ-05）。

### 2.6 假设与依赖

- A1：目标工程可在受控环境本地构建，并能提供测试套件或可自动生成测试。
- A2：攻击模拟所需的 LLM 服务可用且有成本预算；或使用离线 / 私有模型替代。
- A3：Ghidra Headless 在受控环境稳定运行，批量反编译成功率高。
- A4：具备目标平台真机或模拟器用于动态攻击模拟与性能测量。
- A5：用户对目标工程拥有合法所有权，且目标非恶意软件（否则触发 FR-A6 / CQ-03）。

## 3. 功能需求（FR）

> 编号规则见 §1.5。每条需求均给出优先级、可核验的验收标准与验证方式。

### 3.1 输入分析层（Asset Scanner）

**职责**：扫描目标工程，识别敏感资产并分级，输出 `asset_manifest.json`。对应方案 §3.1。

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-A1 | Must | 自动识别工程类型：语言、构建系统、目标平台 | 对基准工程库识别准确率 ≥ 95%；语言覆盖 C/C++/Rust/Python/JS/TS/Java/.NET | UT, IT |
| FR-A2 | Must | 识别敏感资产，三类手段齐备：①字符串类（密钥 / Token / 连接串 / 授权校验文本）②函数类（加解密 / 授权校验 / 算法核心）③数据流类（密钥从生成到使用的路径） | 三类手段均可用；对标注样本**召回率 ≥ 90%**、误报率 ≤ 20% | UT, IT |
| FR-A3 | Must | 敏感度自动分级 P0–P3，并支持人工覆盖 | 每条分级附带可解释证据；人工标注可覆盖自动结果且冲突可追溯 | UT, MR |
| FR-A4 | Must | 识别开源组件并输出 SBOM；开源部分强制标记 P3 且跳过变换 | 输出 SBOM（SPDX 或 CycloneDX）；开源文件在变换阶段零改动 | IT, MR |
| FR-A5 | Must | 输出 `asset_manifest.json` 并通过 Schema 校验 | 产物通过 `schemas/asset_manifest.schema.json` 校验 | UT |
| FR-A6 | Must | 所有权不明 / 疑似恶意目标时拒绝执行并报告 | 触发拒绝条件时中止流程，生成拒绝报告，不产出任何变换产物 | UT, MR |
| FR-A7 | Should | 支持 `assets.yaml` 人工标注，覆盖自动识别结果 | 人工标注优先级高于自动识别，覆盖关系可在报告中呈现 | UT |

**边界条件**：开源组件不得被变换（FR-A4 ↔ CQ-01）；无法判定所有权时默认拒绝（FR-A6 ↔ CQ-03）。

### 3.2 策略决策层（Strategy Engine）

**职责**：依据资产清单与性能预算，生成防护策略组合，输出 `protection_policy.yaml`。对应方案 §3.2。

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-B1 | Must | 内置策略模板库，覆盖 P0–P3 四档组合，YAML 可维护可扩展 | 至少覆盖方案 §3.2 的四档组合；新增模板无需改代码 | UT, MR |
| FR-B2 | Must | 按敏感度自动匹配策略，规则可配置 | 给定 manifest 产出完整 policy，无资产遗漏；匹配规则可通过配置调整 | UT, IT |
| FR-B3 | Should | 在性能预算内优化策略组合（开销预测 + 裁剪） | 预测开销与实际开销偏差 ≤ 30%；超预算时自动降级并告警 | UT, PT |
| FR-B4 | Should | 支持 MTD 多变体：同一工程每次构建产出不同保护变体（`variant_count`） | 生成的 n 个变体两两差异率 ≥ 预设阈值；每个变体功能测试全通过 | IT, AT |
| FR-B5 | Should | 检测策略冲突 / 覆盖缺口并告警 | 已知冲突用例零漏报；覆盖缺口给出可读告警 | UT |
| FR-B6 | Must | 输出 `protection_policy.yaml` 并通过 Schema 校验 | 通过 `schemas/protection_policy.schema.yaml` 校验 | UT |

**关键决策依据**（引用方案 §3.2）：CFF+MBA 在 LLM 攻击成本提升上（约 4.5×）优于单一 Virtualize+MBA（约 1.5×），故 P0 资产采用**组合策略**而非单一策略。

### 3.3 变换执行层（Transform Engine）

**职责**：对白名单资产执行编译级 / 二进制级变换，保证语义等价。这是产品核心执行模块，对应方案 §3.3。

**3.3.1 LLVM IR 变换**

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-C1 | Must | 控制流平坦化（CFF）：将控制流图重构为 switch-case 调度器 | 变换后语义等价（差分测试全过）；反编译后 CFG 复杂度指标显著提升 | UT, FT |
| FR-C2 | Must | 非线性 MBA：阶数 1–4 可配置 | 等价性经 SMT（如 Z3）验证；生成表达式规模随阶数可控增长 | UT |
| FR-C3 | Must | 不透明谓词：插入恒真 / 恒假复杂数学表达式 | 语义不变；谓词无法被简单常量折叠 / 死代码消除消除 | UT |
| FR-C4 | Should | 函数边界扰动：拆分 / 合并函数 | 语义不变；反编译器的函数识别数量 / 边界发生变化 | UT, AT |
| FR-C5 | Should | 数据流噪声注入：插入无语义副作用的冗余数据操作 | 语义不变；引入开销在预算内 | UT, PT |

**3.3.2 代码虚拟化**

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-C7 | Must | 代码虚拟化：原始代码 → 自定义 ISA → 字节码编译 → 嵌入 VM 解释器；支持 x86_64 / ARM64 | 目标函数虚拟化后功能正确；每实例 opcode 映射与寄存器分配随机化（重放攻击不通用） | IT, FT |
| FR-C8 | Should | 虚拟化覆盖率控制：可配置被虚拟化的函数 / 代码比例 | 实际覆盖率与配置误差 ≤ 5%；覆盖率参数生效 | UT |

**3.3.3 对抗性诱导与白盒密码**

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-C9 | Should | 对抗性诱导生成器：生成功能保持但语义误导的变体（参考 SemAder / Acoda） | 功能测试全过；LLM 功能判断出现显著偏差（见 FR-E6 指标）；体积 / 开销增长受控 | AT, IT |
| FR-C10 | Should | 白盒密码模块：AES / SM4 的 S-box 以查找表嵌入并编码隐藏；密钥与算法混合编码，运行时重构、用后销毁 | 加解密自洽；代码与内存中不以明文常量形式出现密钥；使用后内存被擦除 | UT, AT |

**3.3.4 变换框架**

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-C6 | Must | 选择性变换：严格按 `asset_manifest` 白名单施加，非名单代码零变换 | 对非白名单文件做字节级比对，零改动 | UT |
| FR-C11 | Should | 变换插件 SPI：新变换以插件方式注册，不改核心引擎 | 新增一个示例变换无需修改核心引擎代码 | IT, MR |
| FR-C12 | Could | 变换后语义校验钩子：每次变换后可选择性触发测试套件做语义回归 | 可配置触发；失败时按策略回滚或中止 | IT |

**边界条件**：所有变换必须保证语义等价（设计约束 §2.5）；虚拟化对性能影响最大，仅对 P0 关键函数按覆盖率启用。

| FR-E7 | Must | 保护报告：生成 json / markdown / html 三种格式 | 三格式产出且内容一致 | UT |
| FR-E8 | Should | 回归检测：策略变更后自动运行攻击模拟基准 | 触发式回归，指标退化即告警 | IT |

**量化指标定义**（引用方案 §3.5.2）：

| 指标 | 定义 | 目标值 |
| :--- | :--- | :--- |
| Token 消耗倍数 | 分析保护产物的 Token / 分析未保护产物 | ≥ 100x（R3）→ ≥ 500x（v1.0） |
| 分析时间倍数 | 同上，时间维度 | ≥ 10x |
| 函数名恢复准确率 | LLM 恢复正确函数名比例 | ≤ 20% |
| 功能判断准确率 | LLM 正确判断函数功能比例 | ≤ 30% |
| 漏洞发现率 | AI 发现真实漏洞数 / 总漏洞数 | ≤ 10% |
| 二进制相似度评分 | BinDiff / Asm2Vec 等相似度 | ≤ 0.55 |
| 会话上下文消耗率 | 单次独立会话中所消耗上下文的比例；用于「未成功 REA」判定 | 消耗 ≥ 90% 仍未成功 → 判通过 |

### 3.6 对抗策略引擎（Adaptive Strategy Engine）

**职责**：以 AI 对抗 AI 并持续进化，对应方案 §3.6。

| 编号 | 优先级 | 需求描述 | 验收标准 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| FR-F1 | Should | 多 LLM 并行探测：用运行环境可用的多个模型评估策略跨模型泛化性（**不绑定固定供应商**） | 当存在 ≥ 2 个可用模型时并行评估；结果可聚合比较 | IT |
| FR-F2 | Should | 弱点记录与策略调整：记录弱点并给出 / 执行调整 | 弱点可入库；调整建议可一键执行；调整后指标不回退 | IT, MR |
| FR-F3 | Could | 策略遗传进化：维护策略种群，交叉变异与选择 | 完成进化循环；进化后防护得分不劣化 | AT |
| FR-F4 | Could | 策略沉淀与迁移：有效策略入库并推荐给相似项目 | 策略入库；相似项目可获得迁移推荐 | IT, MR |

### 3.7 报告与产物管理

## 4. 外部接口需求

### 4.1 用户界面（CLI）

| 子命令 | 作用 | 关键返回 |
| :--- | :--- | :--- |

| `anti_rea.plan` | 生成策略 | `manifest`、`budget` | `protection_policy` |
| `anti_rea.protect` | 执行变换 | `policy`、`build_cmd` | 产物 + 变换日志 |
| `anti_rea.verify` | 功能验证 | `artifacts`、`test_cmd` | `verification_report` |
| `anti_rea.attack_sim` | 攻击模拟 | `artifacts`、`budget` | `eval_report` |
| `anti_rea.report` | 生成报告 | `run_id`、`format` | 报告文件 |
