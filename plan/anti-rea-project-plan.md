# Anti-REA Skill 详细项目计划

## 文档信息

- **文档版本**：v1.0
- **创建日期**：2026-10-15
- **上游依据**：`anti-rea-plan.md` v1.0（开发方案文档）
- **文档性质**：全生命周期项目计划（阶段 → 任务清单 → 交付物 → 出口准则）
- **执行主体**：AI Agent 主力执行，人工技术负责人评审关键交付物、审批里程碑门禁
- **推进方式**：阶段制 + 里程碑门禁，不设固定周数，时间随执行滚动调整

## 0. 计划说明

### 0.1 本计划的定位

原方案（`anti-rea-plan.md`）是一份**能力模块导向**的技术方案：定义了 6 大模块、变换技术、量化指标与按能力构建的 16 周路线图。本计划在其基础上补齐两件事：

1. **补齐软件生命周期**：原路线图从「搭骨架」直接进入编码，本计划补上需求分析、概要设计、详细设计、Beta 试点、正式发布、运维进化等阶段。
2. **把工作落成可追踪的执行单元**：每个阶段给出任务清单（编号）、交付物、里程碑与出口准则，作为推进与验收依据。

### 0.2 计划原则

- **不设固定周数**：以「阶段 → 里程碑 → 出口准则」驱动；每个里程碑必须满足出口准则，方可进入下一阶段。
- **阶段 / 里程碑级粒度**：任务清单 + 交付物 + 验收标准，不做逐任务工作量估算。
- **验收前置**：每个任务在动手前即可判定「做到什么算完成」；出口准则尽量量化、可核验。
- **门禁不通过不推进**：任一里程碑出口准则未满足，先补缺项，不带着缺陷进入下一阶段。

### 0.3 与原方案的关系

- 技术内容（6 大模块、变换技术、量化指标、技术选型、风险）以原方案为准，本计划不重复展开，只做引用与任务化。
- 原方案第 5 节路线图与本计划的阶段映射见 §1.3。

### 0.4 相比原方案新增的生命周期阶段

| 新增内容 | 说明 |
| :--- | :--- |
| 需求分析阶段（S0） | 原方案无独立需求阶段；FR / NFR / CQ 在此基线化，并建立需求追踪矩阵（RTM） |
| 概要设计阶段（S1） | 将原方案 §2–§4 沉淀为「架构基线 + 数据契约 + 技术选型 PoC」，先给高风险技术去风险 |
| 详细设计阶段（S2） | 原方案 §3 的「详细设计」实为模块功能描述；本阶段产出可直接指导编码的算法级设计 + 测试计划 |
| Beta 试点阶段（S5） | 选取真实工程灰度试用，验证易用性与真实场景效果，而非仅通过内置基准 |
| 正式发布阶段（S6） | 版本策略、制品签名、SBOM、发布渠道、Go/No-Go 决策 |
| 运维与持续进化（S7） | 把原方案 Phase 4 常态化：监控、基准回归、策略库更新、REA 能力追踪 |
| 横切活动（§10） | 风险管理、合规审查、文档管理、配置与变更管理、质量保证，贯穿全周期 |

**目标**：把原方案的项目定位、6 大模块能力、量化指标，转化为带编号、带验收标准、可追踪的需求基线。

| :--- | :--- | :--- |

| RQ-02 | 对标调研 | 复核 skill-guard / Acoda / SemAder / Tigress / OLLVM / VMP / Ghidra / Thales 的可复用与差异化点 |

### 2.2 功能需求基线（FR）

**输入分析层**

| 编号 | 需求 | 验收标准 |
| :--- | :--- | :--- |
| FR-A1 | 工程类型识别 | 正确识别 C/C++/Rust/Python/JS/TS/Java/.NET 及对应构建系统与目标平台 |
| FR-A2 | 敏感资产识别 | 对字符串 / 函数级 / 数据流三类手段均有实现，测试样本召回率 ≥ 90% |
| FR-A3 | 敏感度分级 | 自动给出 P0–P3 评级，并支持人工覆盖 |
| FR-A4 | 开源组件识别 | 输出 SBOM；开源组件强制标记 P3 且跳过变换 |
| FR-A5 | 资产清单输出 | 生成 `asset_manifest.json` 并通过 Schema 校验 |
| FR-A6 | 拒绝执行机制 | 所有权不明 / 疑似恶意目标 → 拒绝并给出报告 |
| FR-A7 | 人工标注支持 | 支持 `assets.yaml` 覆盖自动识别结果 |

**策略决策层**

| 编号 | 需求 | 验收标准 |
| :--- | :--- | :--- |
| FR-B1 | 策略模板库 | 内置 P0–P3 组合模板，YAML 可维护、可扩展 |
| FR-B2 | 匹配引擎 | 按敏感度自动匹配策略组合，规则可配置 |
| FR-B3 | 预算约束优化 | 在性能预算内求解策略组合（开销预测 + 裁剪），并给出预测开销 |
| FR-B4 | MTD 多变体 | 支持 `variant_count`，每次构建产出不同变体 |
| FR-B5 | 冲突与缺口检测 | 检测策略冲突 / 覆盖缺口并告警 |
| FR-B6 | 策略文件输出 | 生成 `protection_policy.yaml` 并通过 Schema 校验 |

| FR-C7 | 代码虚拟化 | 自定义 ISA + 字节码编译 + VM 解释器（x86_64 / ARM64） |
| FR-C8 | 虚拟化覆盖率控制 | 可配置被虚拟化的函数 / 代码比例 |
| FR-C9 | 对抗性诱导生成器 | 生成功能保持、语义误导的变体 |

| FR-C12 | 变换后语义校验钩子 | 每次变换后可选择性触发测试套件做语义回归 |

### 2.3 非功能需求基线（NFR）

| 编号 | 需求 | 量化指标 |
| :--- | :--- | :--- |
| NFR-01 | 性能开销预算 | P2 ≤ 5%、P1 ≤ 15%、P0 组合策略 ≤ 40%（均可配置） |
| NFR-02 | 防护效果 | 迭代 R3：内置模拟 Token 消耗倍数 ≥ 100x；v1.0 目标 ≥ 500x（需外部交叉验证） |
| NFR-03 | 语义保持 | 受保护产物单元测试通过率 100%；差分 fuzz 无行为偏差 |
| NFR-04 | 可复现 | 相同输入 + 策略 + 种子 → 逐位相同产物 |
| NFR-05 | 平台矩阵 | Linux x86_64 / arm64（首要）；Windows x64（次要）；Android / WASM（扩展） |
| NFR-06 | 离线可用 | 除 LLM 攻击模拟外，全流程可离线运行 |
| NFR-07 | 可扩展与规模 | 新变换免改核心；支持千文件级工程，扫描不 OOM |
| NFR-08 | 随机性可控 | 随机种子统一管理；关闭随机即可确定输出 |
| NFR-09 | 自身安全 | 工具自身依赖走 SBOM，无已知高危漏洞 |
| NFR-10 | 安全软件兼容 | 保护产物对主流 EDR 的误报可控，提供签名 / 白名单指引 |

### 2.4 合规与边界需求（CQ）

| 编号 | 需求 | 验收标准 |
| :--- | :--- | :--- |
| CQ-01 | 开源许可证合规 | 不混淆开源部分、保留许可证声明，输出许可证清单 |
| CQ-02 | 出口管制 | 加密强度按目标市场分级配置，保留合规审计日志 |
| CQ-03 | 使用边界 | 拒绝恶意软件 / 所有权不明目标，拒绝行为留痕 |
| CQ-04 | EDR 误报缓解 | 提供签名支持与白名单申请流程文档 |

### 2.5 交付物与出口准则

**交付物**：SRS（软件需求规格说明书，含 FR/NFR/CQ 全表）、用例文档、RTM、合规需求清单。

**出口准则（M0）**
- 全部 FR / NFR / CQ 均有唯一编号与可核验的验收标准；
- 每条需求在 RTM 中关联到设计与测试用例（可为占位）；
- 需求评审通过并经人工负责人确认，形成基线；
- 无「无法验收」或「边界模糊」的需求遗留。

## 3. 阶段 S1：概要设计

**目标**：把需求基线转化为稳定的架构与接口契约，并对高风险技术先做 PoC 去风险，避免「设计完才发现做不出来」。

### 3.1 任务清单

| 编号 | 任务 | 交付要点 |
| :--- | :--- | :--- |
| HD-01 | 架构细化 | 组件图、依赖方向（单向）、跨模块数据流图；明确六层职责边界 |
| HD-02 | 技术选型 PoC | 3 项高风险先验证：LLVM Pass 可行性、Ghidra Headless 自动化、DEAP 进化原型 |
| HD-03 | 模块接口契约 | 每个模块的输入 / 输出 / 错误码 / 前置条件，冻结为契约 |
| HD-04 | MCP Server API 设计 | 工具清单与入参 / 出参 Schema（§3.4） |
| HD-05 | 数据模型与 Schema | `asset_manifest` / `protection_policy` / `eval_report` / `strategy_kb`（§3.3） |
| HD-06 | 变换插件 SPI | 插件注册、能力声明、生命周期钩子 |
| HD-07 | 仓库结构与骨架规范 | 目录骨架、语言分层、构建方式（§3.5） |
| HD-08 | 架构决策记录（ADR） | 关键取舍（如自研 VM vs Tigress、LLVM 版本锁定）逐条留档 |
| HD-09 | 部署架构 | 本机 CLI / 容器化 / MCP 接入 Agent 三种形态 |
| HD-10 | 概要设计评审 | 架构评审 checklist 通过 |

### 3.2 技术选型 PoC 清单（去风险重点）

| PoC | 要回答的问题 | 通过标准 |
| :--- | :--- | :--- |
| PoC-1 LLVM | 目标 LLVM 版本上写自定义 FunctionPass、正确遍历与改写 IR 是否顺畅 | 能对一个样例函数完成一次 CFF 式改写并保持可编译可运行 |
| PoC-2 Ghidra | Headless 模式能否批量反编译并稳定产出可喂给 LLM 的文本 | 对样例二进制批量反编译成功率 ≥ 95% |
| PoC-3 DEAP | 用 DEAP 表达「策略基因」并跑通一次进化循环是否可行 | 完成一轮种群初始化 → 评估 → 交叉变异 → 选择 |
| PoC-4 白盒密码 | 查找表编码方案是否可落地且性能可接受 | 完成一个 AES 查找表编码原型的加解密自洽 |

> PoC 结论写回 ADR；若某项 PoC 不通过，调整技术方案后再进 S2，不带风险进入编码。

### 3.3 核心数据模型（Schema 概要）

| 对象 | 文件 | 关键字段 |
| :--- | :--- | :--- |
| 资产清单 | `asset_manifest.json` | `schema_version`、`project{language,build_system,target_platform}`、`assets[{id,path,type,sensitivity,evidence,license,protection_hint}]`、`summary` |
| 防护策略 | `protection_policy.yaml` | `target`、`performance_budget`、`assets[{path,sensitivity,strategies[],options}]`、`mtd{variant_count}`、`verification`、`build{hooks}` |
| 评估报告 | `eval_report.json` | `baseline`、`protected`、`metrics{token_ratio,time_ratio,name_recovery,function_judgement,vuln_discovery,bin_similarity}`、`per_asset`、`llm_providers` |

## 5. 阶段 S3：编码实现

**目标**：按三个迭代里程碑（R1 → R2 → R3）交付可运行、可验证的软件增量，直到功能冻结（M5）。

### 5.1 开发规范（编码前先落地）

| 事项 | 规范 |
| :--- | :--- |
| 目录结构 | 按 §3.5 骨架；模块内聚，跨模块只经受控接口调用 |

在方案原有 6 项风险基础上，补充以下技术 / 工程风险：

| 风险 | 影响 | 应对 |
| :--- | :--- | :--- |
| LLVM 版本升级导致 Pass 失效 | 构建断裂 | 锁定 LLVM 版本；维护升级适配分支；Pass 单测覆盖 |
| Ghidra Headless API 变化 | 攻击模拟不可用 | 锁定版本 + 适配层封装，隔离外部 API |
| LLM API 成本 / 配额 / 可用性 | 评估与进化受限 | 设预算上限、结果缓存、小模型预筛后再上大模型 |
| 白盒密码学术有效性争议（可被 DCA / 侧信道） | 保护被高估 | 明确定位为「提高提取成本」而非「抗提取」，写入威胁模型 |
| Windows 上 LLVM 工具链复杂 | 开发受阻 | 开发优先 WSL2 / Linux，Windows 作为适配目标 |
| 效果指标被「作弊式」优化（如纯膨胀代码刷 Token） | 指标失真 | 联动约束体积增长与运行时开销，纳入同一适应度 |
| 对抗诱导 / 混淆产物触发 EDR 误报 | 分发受阻 | 提供签名与白名单流程；误报纳入兼容性测试 |
| 大工程扫描 / 变换与增量变换的性能瓶颈 | 不可用 | 增量扫描 + 缓存 + 并行化，纳入稳健性测试 |

> 风险登记册每里程碑回顾一次，逐条更新「状态 / 概率 / 影响 / 应对进展」。

## 11. 度量体系

| 维度 | 指标 | 用途 |
| :--- | :--- | :--- |
| 产品 - 防护效果 | Token 消耗倍数、分析时间倍数、函数名恢复准确率、功能判断准确率、漏洞发现率、二进制相似度 | 判定「逆向成本 > 收益」是否成立 |
| 产品 - 代价 | 运行时开销、体积增长、虚拟化覆盖率 | 与防护效果联动，防作弊式优化 |
| 过程 - 质量 | 单测覆盖率、缺陷密度、缺陷逃逸率、评审覆盖率 | 评估工程健康度 |
| 过程 - 进度 | 里程碑达成率、出口准则一次通过率、需求稳定度 | 评估计划执行情况 |
| 过程 - 效率 | CI 时长、单次保护平均耗时、LLM 消耗成本 | 评估工程效率与成本 |

> 无固定周数，进度用「里程碑完成度 + 出口准则通过情况」衡量，而非时间消耗。

## 12. 计划维护

- **回顾机制**：每个里程碑完成后做一次回顾，更新本计划、风险登记册与 RTM；
- **计划变更**：任何阶段划分、里程碑或出口准则的调整，须记录到下方修订记录并经人工负责人批准；
- **动态时间**：不设固定周数，若某阶段出口准则久攻不下，优先重新评估方案（回到 S1/S2）而非强行推进；
- **文档同步**：本计划与 `anti-rea-plan.md` 冲突时，技术内容以原方案为准，阶段与流程以本计划为准。
